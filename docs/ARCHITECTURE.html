VLEO integrated design tool · architecture

How the tool is built, end to end

What each part is, where its code and data live, how a number becomes a picture and a picture becomes a shared result, who can reach what, and the order in which the rest is built.

Answer first. The tool has three parts. The backend is the engine: one Rust kernel that computes every number, and the local server that answers the browser. The frontend is HTML: the pages, charts, forms and — as they arrive — animations and 3D views that show what the engine produced. The data part keeps everything: the design in git, reference data in hashed bundles, and each person's case and results as files, optionally in a shared folder. The three meet only at written contracts, so each can be worked on by people with different backgrounds, at the same time, without breaking the others.

Kind: reference + explanation · For: everyone — users, maintainers, developers, and anyone deciding how to extend the tool

1 · THREE PARTS

Frontend, backend and data — and the contracts between them

Answer first. Each part has its own folders, its own skills and its own checks. What crosses between them is fixed in writing: the frontend reaches the backend only through the HTTP API under /v1 and a small set of file formats; the backend reaches stored data only through the storage interface in vleo-data. Change anything inside a part freely; change a contract only with both sides agreeing.

2 · WORKING IN PARALLEL

How the frontend and the backend are developed at the same time

Answer first. Both sides build against the same written contract. The backend proves it keeps the contract with contract tests; the frontend builds against recorded example answers served by a small mock engine, so a frontend developer never has to compile Rust and a backend developer never has to open a browser. Inside /v1 a change may only add; anything that removes or changes meaning becomes /v2, served beside /v1 for one release while the frontend moves over.

PieceWhat it isState
The HTTP API30 routes under /v1, JSON, served from the same origin as the pages — so the browser's cross-origin rules never apply.exists
Version and identity/v1/version reports the engine version, kernel and graph hashes; a node page carries its sheet hash and refuses to show a stale one.exists
contract/Every route in routes.toml with the requests the tests make; a JSON Schema per kind of JSON answer; the CSV file formats (a result, a sweep, the case); answers recorded from the real engine. contract/README.md is the whole of it.exists

The versioning ruleWithin /v1: add routes and fields only. Remove or re-mean anything: /v2 beside /v1 for one release. The page reads contract from /v1/version and names a mismatch instead of misbehaving.exists
OwnershipCODEOWNERS names a frontend team (web/, panels/, their checks, the mock engine), a backend team (engine, server, generators) and a data team (vleo-data, bundles/); contract/ names both sides, and its formats all three. Markup owned by the frontendEvery page the tool writes as a file — node and lesson forms, a saved result, the role guides, a row's page, the readers' pages — is one template, web/page.html, with four slots, and what each puts in it is a parts file in web/pages/: every word and tag, by name, with its style and its script (vleo_sheet::shell). A generator decides only which part, how often and with what. A test refuses a generator that writes a tag, a part nothing uses, style or script in Rust, and a page of its own; every page came out byte for byte what it was, the 1,396 committed row pages and the three guides among them. The face's type is bundled in web/fonts. Lessons work the same way: content in lesson.toml, every part drawn by web/js/components.js.done, 9d–9g

A frontend change, alone

New chart style, a better layout, a 3D camera control: edit web/, run the panel checks against the mock engine, open a pull request. No backend reviewer, no Rust build.

A backend change, alone

A faster resolver, a new node, a fix in a relation: edit crates/, run the gate, tests and contract tests. If every answer still matches its schema, nothing in the frontend can notice.

A change to both

A new field in /v1/run: first a pull request to contract/ adding it (both sides review), then the backend fills it and the frontend shows it — in either order, because an added field breaks nobody.

A breaking change

Renaming a field: /v2 is added beside /v1; the frontend moves in its own pull request; /v1 is removed one release later. Nobody has to merge on the same day.

3 · WHERE EVERYTHING LIVES

Four places data lives, one engine, several faces

Answer first. Everything the tool knows lives in exactly one of four places, and each has one rule for how it changes. The design and the reference data change only by review and arrive with a release. A person's case and results are theirs and live outside the repository. Personal reading state never leaves the browser it was made in.

4 · VISUALISATION

How a picture is made: data, then a description, then drawing

Answer first. A figure is never stored as a picture. The engine produces the data; a small description says what to draw from it — the kind of mark, axes with units, the answer line, the rows it came from; a renderer draws it when someone looks. The same description serves an interactive chart in the browser, a static SVG in a report, a PNG for slides, an animation (the description plus a time axis) and a 3D view (geometry plus the same time series). A picture can always be redrawn from data; data can never be recovered from a picture.

Output kindStored asDrawn by
Numbervalue, unit, verdict, provenance — the values CSVevery face
Tablecolumns with units, rows — CSV; Parquet when largetable view; Excel; Python
Figure — line, scatter, bar, band, heatmapthe description (JSON) + data filesbrowser canvas; SVG in reports; PNG export
Textanswer first, findings, notes with claim tags — Markdown subsetevery face
Animationthe figure description plus a time axis; frames are slices of the data, loaded in chunksthe player in the page; MP4 or GIF only as an export, never the record — a video cannot be zoomed, checked or re-coloured
3D scenegeometry as glTF 2.0 (.glb); motion — attitude, position — as time series in a declared frame (ECI, ECEF or body, from vleo-units::frames)the 3D viewer (WebGL, bundled so it works offline); Blender or any glTF viewer

3D, first

The spacecraft body and its appendages from the design's own dimensions; its attitude and position over time; the orbit around a plain Earth; a fixed set of camera views that the checks compare against approved references.

3D, as it grows

Subsystem meshes, ground tracks and sensor footprints on a textured globe, eclipse and lighting, the drag and atomic-oxygen field over the surfaces, several design variants side by side. Each is a new kind of geometry or series in the same format, not a new viewer.

Today the solar figures compute their own statistics in the browser (about 75 places in web/js/solar.js). Those numbers move into the kernel with tests (phase 10), so the frontend only draws and every figure can be reproduced from Python or the command line.

5 · PAGES AND HTML

How a node page is made, including rich interactive lessons

Answer first. Nobody writes HTML for a page. An expert writes content through a form — text, equations, stories, "try it" widgets declared as sliders for these inputs, show these outputs, diagrams as SVG files. A generator assembles the page from a component library that frontend developers build once and test. When a page needs something new, it is added to the library once, and from then on any page can use it by name.

What the expert writes

  • Text for each station, with claim tags: sourced, derived, declared, illustrative
  • Equations, and the source each comes from
  • Widgets as declarations: sliders for these input rows, show these output rows, draw this figure
  • Diagrams as SVG files; stories; check-yourself questions

What frontend developers build once

  • Components: station, answer-first, figure, table, equation, widget, animation, 3D view, story, check-yourself, references, claim tag, depth switch
  • One page template used by node pages, lessons, forms, the case page, result reports, guides and the manual
  • A gate check that refuses a page building a component by hand, or a formula written inside a page
A rich page as one self-contained fileThe same page built this way
≈ 265 KB, fonts and code inside≈ 30 KB of content; the rest shared
its calculators carry their own formulaswidgets computed by the kernel — they cannot disagree with the tool
fonts fetched from the internet at every openfonts bundled with the tool; works offline, contacts nobody
edited as one large HTML fileedited as content through a lesson form, reviewed like a node form

The first lesson is Eight loops, one beam, on the propulsion subsystem's row. A group has no sheet, so a lesson cannot hang on it; the row is l3_prop_interface, the subsystem's interface, and its form is made. Its physics is checked against the rows that exist first; rows it needs that do not exist yet (the RF circuit, the grids) arrive as new-node forms before the lesson that uses them.

6 · DATA AT SCALE

Keeping everything the tool makes, without flooding

Answer first. Runs are deterministic: the same version and the same inputs give the same numbers, every time. So what cannot be recomputed — who ran what, on which inputs, what they concluded — is kept forever and small; the heavy numbers are kept while recent or pinned, and recomputed on demand after that.

WhatMeasuredKept how
A case — all 128 inputs9 KBEach distinct set stored once, by hash. A run records the hash and only the values that differ from that release's defaults.
A saved resultfolderOne folder per question: result.csv, sweep.csv for a sweep, and report.html — the one file to send, which draws its sweep and uploads back whole. Kept once: the row, the inputs, the engine (its code included), the tree, the data and what a sweep moved are one key, and a question already kept is shown from its result — named on screen — rather than run again. done
Result summary≈ 2 KBAlways. KPIs, verdicts, what was blocked, chain hash, input hash, who, when, tags, pin.
All 1,396 row values of a run182 KB · 27 KB compressedKept whole while recent (30 days, VLEO_KEEP_DAYS) or pinned; after that, when the tool starts, an unpinned result thins to its summary — the inputs it ran on, its answer, what could not run — and says so on its page and in its report. A thinned result is not offered as a kept answer, so asking its question again runs it. done Stored as plain CSV, not compressed: compression waits for a folder where the size is felt.
Figures, sweeps, animation frames—Described by the engine, not invented by a page: a figure description (crates/vleo-modules/src/figure.rs, in the contract) says the kind — line, scatter, bar, heatmap, animation, 3D scene — its axes and units, every series and the row it shows, and every refused point with why. A saved sweep is served as one and drawn from it; the other kinds are in the model and the contract now, drawn from phase 9. done Frames and scenes are saved with their result when a figure needs them — the outputs the figure needs, not every row at every point.
Large arrays—Parquet above ~100,000 values — columnar, typed, several times smaller, read directly by Python, MATLAB and Excel. Loaded into a page as an overview first (each pixel's minimum and maximum, so no peak is lost) and detail on zoom.
The index of all results—A small index file, .index.tsv in the results folder, rebuilt from the results when lost or when the folder holds anything it does not. Finding a kept question reads it, not every result. done Moves to SQLite — one embedded file, no server — past ~50,000 results or when queries across runs are needed.
Crash logs< 1 KB each~/.vleo/log/, the newest 50 kept.
Pinned and shared results—Never thinned, never deleted by the tool. Pin on a result's page, or POST /v1/results/pin. A folder named by VLEO_RESULTS is treated as shared: kept whole unless VLEO_KEEP_DAYS is set too. done

No database server

The design stays in git, where history, review and blame are free. Reference data stays in hashed bundles. Nothing on the physics path waits on a network. An embedded SQLite index is the one database the tool may take on, and only at the size where files stop being quick to list.

One storage interface

Saving, listing, opening and thinning results go through vleo-data, which the server, the command line and Python all call. Files today; SQLite or a team server later, without touching the engine or the pages.

7 · ACCESS, SYNC AND MAINTENANCE

Who reaches what, and how it stays in step

Answer first. Everyone gets the tool from one place — a release — and nobody has to install anything just to read. The design reaches people as a new version; results reach people through a shared folder or as a single file; pages and reports open in any browser.

8 · THE SCRIPTS

A node's journey, and every script able to explain itself

Answer first. Every command says, in the same way, which step it is on, what it read and wrote, and — if it stops — which step, why, what state the files are in, and the exact command to try again. One table in the code describes every script; the help text and a generated docs/PIPELINE.md come from it, and a test fails if they ever disagree.

What a writing command prints when a step stops — real output of xtask publish on a row that is already published:

xtask publish sw_ap_design 1/2 · read the sheet sw_ap_design — Ap design value 2/2 · publish, generate and gate — stopped why this row is not ready to publish — this row is already 'published'; … files as they were — a publish that does not gate is put back whole retry `cargo run -p xtask -- declare sw_ap_design` says what is still open; then … code xtask/src/main.rs — the step "publish, generate and gate" in cmd_publish trace target/xtask-trace/2026-09-29T18-26-26Z-publish.log

For every command

  • xtask explain <command> — its stage, what it reads, writes and checks, how to undo it, its steps and where its code is; explain alone, the whole journey
  • --dry-run — its own check where it has one, otherwise the plan; nothing touched
  • a trace of each writing run in target/xtask-trace/, the newest 50; xtask trace shows the last
  • docs/PIPELINE.md — the table as a page, regenerated by xtask pipeline

For every node

  • xtask why <node> — every recorded version and who made it, the commits that changed it, its approvals, how its code came to be, and its gate, run now
  • step names in the code equal the printed names — a test holds them — so an error message finds its line

9 · WHEN SOMETHING BREAKS

A bug ends one request, leaves a file to send, and never half-writes data

Answer first. A bug in the tool is a Rust panic. It is caught where it happens — per request in the server, at the C boundary — written to a crash log a person can send, and answered with a message that says so; the tool keeps running. Every write of a person's data is whole, so a crash at any moment leaves each file either as it was or as it should be.

MechanismWhereWhat it guarantees
Unwinding release buildCargo.toml [profile.release]A panic can be caught at all. Under the earlier panic = "abort" one bug in any request closed the whole daemon.
One request at a time, guardedvleo-server/src/http.rs — handledA bug answers that request with a 500 (JSON for /v1, naming the crash log); the next request is served.
Connection places given backhttp.rs — OpenPlaceReleased however a connection's thread ends; bugs cannot use up the 64 places until every connection is refused.
The C boundaryvleo-ffi — guardedA bug becomes VLEO_INTERNAL and a message for MATLAB, Simulink or a C program; it never unwinds into the caller.
Crash logvleo-data/src/crash.rsOne plain-text file per bug in ~/.vleo/log/ (or VLEO_LOG): program, version, time, thread, message, line of code. Newest 50 kept.
Whole writesvleo-data/src/whole.rs — write_wholeCase, results, backups, the data lockfile and the command line's saved files are written aside, flushed and renamed over: a reader — this tool, another laptop, a sync client — never sees a file half written.
Paths from the environmentvleo-data — case_path, results_path, log_pathA variable set but empty counts as unset, so a stray VLEO_RESULTS= never sends results into whatever folder the tool was started in.

Each guarantee has a test that was run against a deliberately broken version and went red. Errors outside the kernel are still passed as text in about 130 places; typed errors per crate follow in phase 11.

10 · ROADMAP

Every phase, in order

Answer first. Nothing is rewritten; each phase adds to what exists. Safety first, then what everything else is built on — scripts that explain themselves, the frontend–backend contract, then the storage and output model — so that later additions only add new kinds of thing and never change the ones before.
