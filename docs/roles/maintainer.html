your role, in four steps
1

Say it simply

This is the print shop. The pages come from the people who own them, filed on the shared drive; the shop prints the book that reads them — a release — and sends it to everyone.

illustrative — an analogy, see step 3 for where it stops

2

Now the real thing

You do

  • Build a node from its method with build-node when its method is new.
  • Merge each pull request once every check is green.
  • Release with ship; publish and share the four files.
  • Pack the drive from the release, and share it.
3

Where the simple picture breaks

‘Every step is a command’ stops where a release needs new code or a check fails for a reason of its own. Those are the developer's work on the code, with the command's output. On the switch-over day this guide retires (docs/PLAN_1_0.md, phase H).

You never

  • Edit a group's release — it comes from the group, sealed, and is never changed after.
  • Change a tolerance to make a test pass — that is a physics question for the node's engineer.
  • Skip or silence a failing check; diagnose it as code, with its output.
4

Try it · predict first

Every check on a pull request is green, but the reviewers CONTRIBUTING names have not looked. The change is small. Can you merge?

Say your answer, then open

Not yet. Green is the machine's half; the review is the person's. A small change still needs its reviewers, because size is not what decides whether it is right.

common wrong idea

“A green pull request is ready to merge.”

Green says the change is consistent, not that it is right. A change to the code also needs the reviews CONTRIBUTING sets, by the people it names.

In the browser

Everything anyone using the tool does: read the design, set the inputs, run, keep what a run returned. Nothing in the browser changes the design. What you set and what you keep are yours and stay on your machine; what the design is changes only in its owners' own files, sealed as each group's release and taken into today's design from the shared drive.

Open the tool how-to

answer firstStart the tool with one command and open the address it prints. It never writes the repository: what you keep — the case and your results — stays on your machine under ~/.vleo.

The tool is one program on your own machine. It serves this page and computes every number on it, from one address, with no internet and no database. It listens on 127.0.0.1 only, so nobody else on the network can reach it.

It never writes the repository. The two things you can keep — the case you run on and the results you save — are kept outside it, under ~/.vleo/, so a checkout stays exactly as it was released and git status is empty however much you use the tool. The status card at the top of this manual says where this copy keeps them.

  1. Start it. It prints the address it got — the first free port from 7777 upward.
    cargo run --release -p vleo-daemon
    starts the tool
  2. Open the address it printed, normally http://127.0.0.1:7777.
  3. In a Codespace there is nothing to type: the tool is already running and port 7777 opens as a preview.
  4. Without a repository, the tool comes two ways. The one file for every laptop: python -m pip install vleo-<version>-py3-none-any.whl once, then python -m vleo — it runs inside Python, so Windows has no new program to stop. Or a kit, the zip for your system: double-click Start VLEO.exe on Windows, or run ./start.sh on macOS and Linux. Either opens the page itself; START_HERE.md says the rest.

Who does what explanation

answer firstFive roles. The programme manager, the system engineer, each subsystem engineer and each node engineer own the design and use the tool; a group's work reaches the design as its sealed release, put on the shared drive, where the tool takes it into today's design when it opens. The developer maintains the code and releases the tool — and writes what no routine can: code, checks, the tool itself. Each role has a deputy who may act for it.

The line between the roles is the line between owning and using the design, moving a change through, and building the machinery. The design's own roles follow the tree: the programme manager owns the management side, the system engineer the whole spacecraft and the one release everyone works from, each subsystem engineer their group's branch, and each node engineer their nodes (docs/OPERATING_1_0.md, section 2).

Everyone uses it. Anyone can set the inputs — by hand or as a CSV — run any row on them, save what the run returned and send it on, and look at a result somebody else saved without running anything. When a node is wrong, missing or unfinished, its node engineer — the person who knows the answer — changes it in the node's own file, and their subsystem engineer seals the group's work as a release and sends it.

A sealed release goes on the shared drive, in its group's releases/ folder. When the tool opens on the drive it builds today's design from every group's latest sealed release that passes its checks — its seal, its content, each node against the design — and says which release each group's part is, and why one was refused. Nobody takes a release in by hand. From the switch-over on, each owner signs their own files in the application, and the developer maintains only the code.

The developer builds the machinery. A method that needs maths the kernel does not have needs code in the kernel; a check that fails for a reason not in the release needs a diagnosis; the tool's pages, pictures, checks and generators are designed and improved. All of it through the gate and a reviewed pull request.

There are three guides — for the engineers, docs/roles/user.html; for the releases until the switch-over, maintainer.html; and for the developer, developer.html — generated from this manual, so the three can never disagree with it.

What the browser will not do reference

answer firstThe browser never changes the design. Each thing it will not do has a place it is done instead, and for anyone using it that place is almost always the node's own file, written by its node engineer.

The browser never changes the design: not a field, not a row, not the tree. That is not to keep anybody out. A change to the design has to be checked against every row that reads it, implemented, given evidence, and released so that everyone runs the same thing — and a change typed into one copy of the tool does none of that. So each one below has a place it is done instead, and for anyone using it that place is almost always the node's own file, taken in with its group's release.

The fields a group's release cannot change — the ones that move a row in the tree or change who owns it — are listed live under Reference, each with its reason.

Maintaining the repository

The routine that moves the tool to everyone's copy: build a node from its method, cut a release, build the kits, pack the drive, share. Every step is one command, and each does its whole step or nothing and says what to do next. Nothing here writes code — what needs code goes to a developer, with the output that says why.

Check a node's method against its node engineer's cases how-to

answer firstRun method with the node's id. It checks the method and runs every one of the node engineer's cases through it — the same check the node engineer saw in the group's application, and the one the gate refuses on.

The gate refuses a node whose method does not check, whose cases disagree, or that has fewer than three answers and one refusal. A case that disagrees is the node engineer's to settle — their code, their method or their expected value is wrong — so it goes back to them with the line printed, never to a tolerance.

  1. Check one node's method and cases.
    cargo run -p xtask -- method orbit_velocity
    safe to run — only reads
    prints each case with what the node engineer's code gave and what the method gives; for a method transcribed from code, what it is held to instead; or says the node has no method yet

Build a node from its method how-to

answer firstbuild-node does this for one node. Every stage must pass before the next runs, and the node is connected to the rest of the design only at the end.

M the method runs on the node engineer's cases. G1 the method is translated, by fixed rules, into a kernel function in vleo-core::physics::methods, until the translation goes in phase E. T1 the node, guards and all, must reproduce every case; T2 the translation must give the method's own answer to the last bit, around every case. T3 the node engineer's own code is run again where it can be. I1 only then is the node checked in the tree, and the rows that read it are named.

A case that fails is the node engineer's to settle. A translation test that fails is a translator defect, for a developer. Neither is ever a tolerance to change.

  1. Rerun every node engineer's code on the cases recorded from it.
    cargo run -p xtask -- rerun --all
    safe to run — only reads
    says, per node with cases, whether the node engineer's code still gives them, or why it could not be run here

Release a version how-to

answer firstOnce maintainer and developer are merged into main, run ship on an up-to-date main. Merge the pull request it opens the way to and tag the merge commit; the release pipeline builds and publishes the four files itself.

ship cuts release/<version>: the de-risking narrative regenerated, every node version still marked next stamped with this release, regeneration, the gate, the tests, one commit, pushed.

The merge is the decision. The release workflow builds only a commit that a merged pull request put on main, and refuses anything else before it builds (docs/RELEASE_SETUP.md). After the merge, tag the merge commit (the commands ship prints). The release workflow then builds the three kits and the one-file package, installs the package on Windows, macOS and Linux, and publishes the release with the four files attached; share the .whl with everyone.

Choosing the number: the middle number for new behaviour or a change in how everyone gets the tool, the last for fixes.

  1. Cut the release from an up-to-date main.
    cargo run -p xtask -- ship <version>
    changes files
    creates release/<version>, stamps, regenerates, gates, tests, commits and pushes
  2. After its pull request is merged: tag the merged main.
    git switch main && git pull origin main && git tag v<version> && git push origin v<version>
    changes files
    the tag starts the release workflow, which builds the four files

What goes to a developer reference

answer firstAnything that needs code or judgement about the machinery: a method that needs a relation the kernel does not have, a check that fails for a reason of its own, a merge conflict, a change to the tool itself. Hand over the command and its output.

A new relation. A node whose method calls on maths the kernel does not have needs a function in vleo-core::physics first — a developer's step, and a reviewed change every node reads.

A failing check. The gate or a test fails for a reason in a node, a generator or the pipeline. The output names it; hand it over with the branch.

A merge conflict in the code.

The tool itself — its pages and pictures, the commands in this layer, the checks, the release pipeline. Those are code, reviewed as code.

When something goes wrong reference

answer firstThe usual failures, each with what it means and what to do. Almost every refusal names the field and the rule, and that line is usually the whole answer.

The tool will not start: nothing was free. It tries sixteen ports from 7777 upward. Something else is holding them — often an earlier copy of the tool. Stop that one, or set VLEO_PORT to start somewhere else.

An uploaded case or result is refused. Every refused row is named, with why. A case is all or nothing, so correct the named rows and upload it again. A file from an older release is carried over rather than refused; one the tool did not write — no #! result line — is not a result at all.

A group's release is refused on the drive. Today's design names the group, the release and why — an input naming a row that does not exist or one of a different quantity, a broken seal, an assistant's method — and builds that group's part from its last good release. The fix goes back to the group.

The checks refuse a row. Each failure names the field and the rule. Read that line before anything else; it is almost always the whole answer.

A row prints INACTIVE and does not answer. Its relation is written but nobody has derived it: the sheet has no [theory] block saying why it is this relation. That is a person's work, supplied by the node's engineer, never something to work around — and every row that reads it is blocked, by name, until it is done. active lists each such row and how many rows wait on it.

A sweep answers no point. Every point is still recorded, with why: blocked when a row on its chain does not answer, or the bound and its reason when the value is outside the declared range of the row being swept.

A command warns that the hooks are not wired. Run setup once in this checkout.

The commit hook refuses a message. It must read type(scope): a sentence, and tools/commit_message.py --types prints every type and scope it accepts.

A number looks wrong. Run the row in the terminal, read its credibility line and which factor governs it, and look at the chain behind this number — every value that reached it, with each one's own credibility. If the design is what is wrong, that goes to the node's engineer.

  1. Start the tool on another port.
    VLEO_PORT=8080 cargo run --release -p vleo-daemon
    starts the tool
  2. Every row that is written but does not answer, and how many rows wait on each.
    cargo run -p xtask -- active
    safe to run — only reads
    it says: undefined — the relation is stated and never derived
