answer first declared · the repository's rules

You move each change through: take a node form in, send its author a preview, record their approval, merge, release, share. Every step is one command — take, preview, approve, queue, ship — and each does its whole step or nothing and says what to do next. You write no code.

your role, in four steps
1

Say it simply

You run the post office and the print shop. Forms come in; each goes into its own envelope — a branch. The author sees a proof — the preview — and signs it — the approval file. When you choose, everything signed is printed for everyone — a release.

illustrative — an analogy, see step 3 for where it stops

2

Now the real thing

You do

  • Save each form you receive into forms/ and run take on it.
  • Send back the note take writes when a form cannot be taken.
  • Send the author their preview; record the approval file they return with approve.
  • Merge each approved pull request once every check is green.
  • See what is waiting with queue; release with ship; publish and share the four files.
3

Where the simple picture breaks

‘Every step is a command’ stops where a form needs new code, where a check fails for a reason not in the form, or where two forms conflict. Those go to a developer, with the command's output.

You never

  • Edit a node's files by hand — the form is the only way in.
  • Merge a form branch without its author's approval of that exact build.
  • Change a tolerance to make a test pass — that is a physics question for the node's owner.
  • Skip or silence a failing check; hand it to a developer with its output.
4

Try it · predict first

Every check on a form branch's pull request is green except ‘the author approved this exact change’. The author said on the phone it is fine. Can you merge?

Say your answer, then open

Not yet. Ask them to press Approve in the preview and send the file — then run approve. The check is the record that they tried this exact build; a phone call leaves none.

common wrong idea

“A green pull request is ready to merge.”

Green says the change is consistent, not that it is right. A form branch also needs its author's approval of the exact build — the check named ‘the author approved this exact change’ says whether it has one.

In the browser

Everything a team using the tool does: read the design, set the inputs, run, keep what a run returned, and ask for a node to change. Nothing in the browser changes the design. What you set and what you keep are yours and stay on your machine; what the design is changes only through a node's form, which the developers check, apply and release.

Open the tool how-to

answer firstStart the tool with one command and open the address it prints. It never writes the repository: what you keep — the case and your results — stays on your machine under ~/.vleo.

The tool is one program on your own machine. It serves this page and computes every number on it, from one address, with no internet and no database. It listens on 127.0.0.1 only, so nobody else on the network can reach it.

It never writes the repository. The two things you can keep — the case you run on and the results you save — are kept outside it, under ~/.vleo/, so a checkout stays exactly as it was released and git status is empty however much you use the tool. The status card at the top of this manual says where this copy keeps them.

  1. Start it. It prints the address it got — the first free port from 7777 upward.
    cargo run --release -p vleo-daemon
    starts the tool
  2. Open the address it printed, normally http://127.0.0.1:7777.
  3. In a Codespace there is nothing to type: the tool is already running and port 7777 opens as a preview.
  4. Without a repository, the tool comes two ways. The one file for every laptop: python -m pip install vleo-<version>-py3-none-any.whl once, then python -m vleo — it runs inside Python, so Windows has no new program to stop. Or a kit, the zip for your system: double-click Start VLEO.exe on Windows, or run ./start.sh on macOS and Linux. Either opens the page itself; START_HERE.md says the rest.

Who does what explanation

answer firstThree roles around one loop. A user uses the tool and, when a node is wrong or missing, fills its form, tries the preview of the change and approves it. A maintainer takes each form in, sends the preview, records the approval and releases. A developer writes what that routine cannot: code, checks, the tool itself.

The line between the roles is the line between using the design, moving a change through, and building the machinery.

A user uses it. Anyone can set the inputs — by hand or as a CSV — run any row on them, save what the run returned and send it on, and look at a result somebody else saved without running anything. When a node is wrong, missing or unfinished, the person who knows the answer fills in that node's form and sends it. They get a preview of their change back, try it, and press Approve — or say what is still wrong.

A maintainer moves each change through. A form that arrives is taken in onto its own branch — checked, applied, tested — and its author is sent the preview. Their approval comes back as a file, and is recorded against exactly the build they tried. Approved changes are merged, and released to everyone when the maintainer chooses. Every step is one command.

A developer builds the machinery. A form that adds a relation needs code in the kernel; a check that fails for a reason not in the form needs a diagnosis; the tool's pages, pictures, checks and generators are designed and improved. All of it through the gate and a reviewed pull request.

Each role has its own guide — docs/roles/user.html, maintainer.html and developer.html — generated from this manual, so the three can never disagree with it.

What the browser will not do reference

answer firstThe browser never changes the design. Each thing it will not do has a place it is done instead, and for a team that place is almost always a node's form.

The browser never changes the design: not a field, not a row, not the tree. That is not to keep anybody out. A change to the design has to be checked against every row that reads it, implemented, given evidence, and released so that everyone runs the same thing — and a change typed into one copy of the tool does none of that. So each one below has a place it is done instead, and for a team that place is almost always a form.

The fields a node form does not carry at all — the ones that move a row in the tree or change who owns it — are listed live under Reference, each with its reason.

Maintaining the repository

The routine that moves every change from a node form to everyone's copy: take the form in, send its author a preview, record their approval, merge, release, share. Every step is one command, and each does its whole step or nothing and says what to do next. Nothing here writes code — what needs code goes to a developer, with the output that says why.

The loop, and where each change stands explanation

answer firstEach form lives on its own branch, form/<author>/<node>, and passes through four stages: taken, previewed, approved, merged. main only ever receives changes whose author tried and approved them; a release takes everything merged since the last one.

Taken. take checks the form and, if it can be applied, puts it on its own branch from a fresh main — applied, regenerated, gated, tested, committed with the author's name, pushed. If it cannot, it writes a note to send back and changes nothing.

Previewed. Every push to a form branch builds a preview by itself: the tool with this one change in it, marked PREVIEW on every view. You send it to the author.

Approved. The author tries it and presses Approve; the file it saves names the exact build. approve records it on the branch — refused if anything has changed since that build — and the pull request's approval check turns green.

Merged, then released. You merge the pull request when every check is green. ship cuts a release from main when you choose; the release pipeline builds the four files; you publish and share them.

Many forms can be in flight at once, each on its own branch, none waiting for another. queue says where each one stands.

  1. Where every form branch stands right now.
    cargo run -p xtask -- queue
    safe to run — only reads

Take a node form in how-to

answer firstSave the form you received into forms/, then run take naming its author. It either puts the change on its own branch — applied, tested, committed, pushed — or writes a note to send back and changes nothing.

forms/ at the top of the repository is where received forms and the notes sent back live; git ignores it, because the form is the author's and is attached to the pull request rather than committed.

take refuses to start with uncommitted changes, so nothing of yours is swept into a commit that names somebody else. It then works in numbered steps — the branch, the form applied, everything regenerated, the gate, the tests, the commit and push — and stops at the first that fails, saying which and how to abandon the branch. A test that fails is a physics question for the node's owner, never a tolerance to change.

Not taken means a field conflicts with a change made since the form was downloaded, an input is not a row of the right quantity, or a relation came from an assistant. The note says which, field by field; send it back, and take the corrected form when it returns — with --again if its branch exists.

  1. Save the filled form into forms/, then take it in, naming its author as they want to be called.
    cargo run -p xtask -- take forms/<file>.node-form.html --for "<author>"
    changes files
    puts the form on its own branch form/<author>/<node>, applies it, regenerates, gates, tests, commits naming the author, and pushes
  2. If it says the form was not taken, send the author the .returned.txt file it wrote beside the form. Nothing was changed.
  3. A corrected form for the same node goes onto the same branch.
    cargo run -p xtask -- take forms/<file>.node-form.html --for "<author>" --again
    changes files
    applies the corrected form onto the branch that already holds the first one

Send the author a preview how-to

answer firstThe push from take builds the preview by itself, in about ten minutes. Download it from the newest green preview run, unzip it once, and send the .whl inside to the author.

The preview is the one-file Python package a release ships, built from this branch, with Windows and Linux engines. Its version carries +preview.<author>.<build>, so it is never taken for a release, and every view shows the PREVIEW banner with the Approve button.

Mac authors: the macOS engines cost ten times the build minutes, so they are built only when asked — Actions → preview → Run workflow → the branch → also build the macOS engines.

How the file travels is yours to choose. Whatever channel you use, send the .whl itself, not a link that needs a GitHub login.

  1. Where this branch's preview is. On main it refuses: previews are built for form branches.
    cargo run -p xtask -- preview
    shows a refusal — it is meant to fail here
    it says: not a form branch
  2. Open the newest green preview run for the branch, download vleo-preview-<author>-<build> at the bottom of the page, unzip it once, and send the .whl inside.

Record the author's approval, and merge how-to

answer firstRun approve on the file the author sends back. It is recorded only if it is for the build of exactly what is on the branch now; then the pull request can be merged once every check is green.

Refused, and why that is right: the file is for an older build (anything pushed since — a fix, main merged in — needs a new preview and a new approval); the author did not tick that they ran it; the file is not an approval at all. Each refusal says which.

The pull request. take and approve both print its link. Merge only when every check is green — among them the author approved this exact change, which reruns the same check the pipeline's way. Use Squash and merge: the author's Form-by: line and the approval travel with it into main.

An approval is a record, not a password: it proves which build was approved, and you, who received it, vouch for who sent it.

  1. Record the approval the author sent back.
    cargo run -p xtask -- approve <file>.toml
    changes files
    stores it in approvals/ on the branch, commits naming the author, and pushes
  2. The same check the pull request runs.
    cargo run -p xtask -- approve --verify <branch>
    changes files
    reads only; shown as not run because it needs a form branch to name

Release a version how-to

answer firstFrom an up-to-date main, run ship with the new version. Merge the pull request it opens the way to, tag the merged main, and publish the four files the release pipeline builds.

ship cuts release/<version>: the de-risking narrative regenerated, every node version still marked next stamped with this release, regeneration, the gate, the tests, one commit, pushed. It lists whose forms the release carries.

After the merge: tag it (the commands ship prints). The release workflow then builds the three kits and the one-file package and installs the package on Windows, macOS and Linux. Its last job, one human says yes, ends red on this repository by design — the files are built. Download the four artifacts, unzip each once, and publish them as the release on GitHub, then share the .whl with everyone.

Choosing the number: the middle number for new behaviour or a change in how the team gets the tool, the last for fixes.

  1. Cut the release from an up-to-date main.
    cargo run -p xtask -- ship <version>
    changes files
    creates release/<version>, stamps, regenerates, gates, tests, commits and pushes
  2. After its pull request is merged: tag the merged main.
    git switch main && git pull origin main && git tag v<version> && git push origin v<version>
    changes files
    the tag starts the release workflow, which builds the four files

When a form changes what a node reads or feeds how-to

answer firsttake prints every input the form declares and whether it connects. A change to what a node reads or feeds can move other nodes' answers, so find who reads it and send those owners the preview too.

The interface check at take is the same one intake runs: each input names a row that exists, of the quantity the node expects. A form that re-points an input or changes a node's output is still one node's change, but its answers travel: reach shows where each answer goes, and CODEOWNERS names who owns the nodes downstream. Send them the same preview; an approval from the author covers the author's node, and the downstream owners' word covers theirs.

  1. Where each answer goes, and which reach no KPI closure.
    cargo run -p xtask -- reach
    safe to run — only reads

Two forms for the same node how-to

answer firstEach still gets its own branch. Merge the first when it is approved; then bring main into the second, send its author a new preview, and record their new approval.

Two authors can send forms for one node at once — each is taken onto its own branch, and neither waits. After the first merges, the second is behind main. Bring main into it (git switch form/<author>/<node> then git merge origin/main); if the same field changed in both, git stops with a conflict — that is a question for the two authors, never a coin toss, and a developer can resolve it once they agree. Anything pushed after an approval needs a new preview and a new approval, so the second author approves the combined change.

Worked example: one form, start to finish tutorial

answer firstAna sends a form for sw_ap_design. It is taken onto form/ana-sharma/sw-ap-design, previewed, approved, merged and released — five commands and two files exchanged. (Illustrative: the steps and messages are real, the people are not.)

1 · The form arrives. Ana's filled sw_ap_design.node-form.html is saved into forms/. take … --for "Ana Sharma" prints each change it applies, runs the gate and the tests, commits feat(mod-solar): sw_ap_design from a node form with Form-by: Ana Sharma, pushes, and prints two links.

2 · The preview. Ten minutes later the preview run is green. Its package vleo-preview-ana-sharma-7 holds one .whl, sent to Ana.

3 · Ana tries it. The banner reads PREVIEW of Ana Sharma's change to sw_ap_design · build 7 · not a release. She runs the node, checks it against the NOAA table she used, presses Approve and sends back vleo-approval-ana-sharma-build7.toml.

4 · Recorded. approve on that file prints approved. Ana Sharma approved build 7. queue now shows the branch as approved — review and merge. The pull request's checks are green, among them the author approved this exact change; it is squash-merged.

5 · Released. When a few forms are merged, ship 0.3.0 cuts the release, its pull request is merged, v0.3.0 is tagged, and the four files are published and shared. Ana installs 0.3.0 over the preview; her inputs and results are still there.

What would have stopped it: had Ana's form re-pointed an input to a row that does not exist, take would have written the note to send back and changed nothing; had a fix been pushed after build 7, approve would have refused her file and asked for a new preview.

What goes to a developer reference

answer firstAnything that needs code or judgement about the machinery: a form that adds a relation, a check that fails for a reason not in the form, a merge conflict, a change to the tool itself. Hand over the command and its output.

A new relation. A form for a new node, or one that changes its maths, can need a function in the kernel and a filled HOLE. take applies the form; declare and publish then say what code is owed — a developer's step.

A failing check that is not the form's. The gate or a test fails on the form branch for a reason in another node, a generator or the pipeline. The output names it; hand it over with the branch.

A merge conflict between two forms, once their authors agree.

The tool itself — its pages and pictures, the commands in this layer, the checks, the release pipeline. Those are code, reviewed as code.

When something goes wrong reference

answer firstThe usual failures, each with what it means and what to do. Almost every refusal names the field and the rule, and that line is usually the whole answer.

The tool will not start: nothing was free. It tries sixteen ports from 7777 upward. Something else is holding them — often an earlier copy of the tool. Stop that one, or set VLEO_PORT to start somewhere else.

An uploaded case or result is refused. Every refused row is named, with why. A case is all or nothing, so correct the named rows and upload it again. A file from an older release is carried over rather than refused; one the tool did not write — no #! result line — is not a result at all.

A form's check shows a conflict. Somebody changed that field in the design after the form was made. Nothing is overwritten: download the node's form again, carry the answer across, and send the new one.

A form's check says an interface does not connect. The input names a row that does not exist, or one of a different quantity. The line says which, and what the row it names actually is.

The checks refuse a row. Each failure names the field and the rule. Read that line before anything else; it is almost always the whole answer.

A row prints INACTIVE and does not answer. Its relation is written but nobody has derived it: the sheet has no [theory] block saying why it is this relation. That is a person's work, supplied through the node's form, never something to work around — and every row that reads it is blocked, by name, until it is done. active lists each such row and how many rows wait on it.

A sweep answers no point. Every point is still recorded, with why: blocked when a row on its chain does not answer, or the bound and its reason when the value is outside the declared range of the row being swept.

A command warns that the hooks are not wired. Run setup once in this checkout.

The commit hook refuses a message. It must read type(scope): a sentence, and tools/commit_message.py --types prints every type and scope it accepts.

A number looks wrong. Run the row in the terminal, read its credibility line and which factor governs it, and look at the chain behind this number — every value that reached it, with each one's own credibility. If the design is what is wrong, that is a form.

  1. Start the tool on another port.
    VLEO_PORT=8080 cargo run --release -p vleo-daemon
    starts the tool
  2. Every row that is written but does not answer, and how many rows wait on each.
    cargo run -p xtask -- active
    safe to run — only reads
    it says: undefined — the relation is stated and never derived
