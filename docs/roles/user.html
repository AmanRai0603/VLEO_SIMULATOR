answer first declared · the repository's rules

You use the tool — read the design, set your inputs, run, keep results — and when a node is wrong or missing, you fill its node form and send it. You get a preview of your change back, try it, and approve it; only then does it reach everyone, in the next release.

your role, in four steps
1

Say it simply

The tool is a shared reference book you can read and calculate with but not write in. To correct a page, you fill in a correction slip — the node form — and hand it in. You are shown the corrected page before it is printed for everyone, and you sign it off.

illustrative — an analogy, see step 3 for where it stops

2

Now the real thing

You do

  • Read the design: the four layers, and each node's page.
  • Set your inputs, run, save results and send them on.
  • Fill a node's form when it is wrong or missing, and send it to the maintainer.
  • In the form, give the method, your code and your test cases — three answers and one refusal — until its check says Sound.
  • Try the preview of your change and press Approve — or say what is still wrong.
  • Install each new version over the old one; your inputs and results carry over.
3

Where the simple picture breaks

‘You cannot write in it’ is about the design, not your own work: your inputs, saved case and results are yours to change freely, and stay on your machine.

You never

  • Edit files inside the tool — a change there reaches nobody and is lost at the next version.
  • Approve a preview you have not run.
  • Put an expected value in a form that came from the tool itself — it has to come from outside it.
4

Try it · predict first

You approved build 7 of your change on Monday. On Tuesday the maintainer fixes a typo in the same node and pushes. Is your approval still good?

Say your answer, then open

No. Your approval is for build 7 exactly; anything pushed after it makes a new build, and you are sent that preview to approve. It costs you a minute and it means nobody can merge something you did not see.

common wrong idea

“If I change something in my copy of the tool, everyone gets it.”

Your copy changes nobody else's. Inputs you set are yours; the design itself changes only through a node form — checked, previewed, approved by you, and released to everyone at once.

In the browser

Everything a team using the tool does: read the design, set the inputs, run, keep what a run returned, and ask for a node to change. Nothing in the browser changes the design. What you set and what you keep are yours and stay on your machine; what the design is changes only through a node's form, which the developers check, apply and release.

Open the tool how-to

answer firstStart the tool with one command and open the address it prints. It never writes the repository: what you keep — the case and your results — stays on your machine under ~/.vleo.

The tool is one program on your own machine. It serves this page and computes every number on it, from one address, with no internet and no database. It listens on 127.0.0.1 only, so nobody else on the network can reach it.

It never writes the repository. The two things you can keep — the case you run on and the results you save — are kept outside it, under ~/.vleo/, so a checkout stays exactly as it was released and git status is empty however much you use the tool. The status card at the top of this manual says where this copy keeps them.

  1. Start it. It prints the address it got — the first free port from 7777 upward.
    cargo run --release -p vleo-daemon
    starts the tool
  2. Open the address it printed, normally http://127.0.0.1:7777.
  3. In a Codespace there is nothing to type: the tool is already running and port 7777 opens as a preview.
  4. Without a repository, the tool comes two ways. The one file for every laptop: python -m pip install vleo-<version>-py3-none-any.whl once, then python -m vleo — it runs inside Python, so Windows has no new program to stop. Or a kit, the zip for your system: double-click Start VLEO.exe on Windows, or run ./start.sh on macOS and Linux. Either opens the page itself; START_HERE.md says the rest.

Who does what explanation

answer firstThree roles around one loop. A user uses the tool and, when a node is wrong or missing, fills its form, tries the preview of the change and approves it. A maintainer takes each form in, sends the preview, records the approval and releases. A developer writes what that routine cannot: code, checks, the tool itself.

The line between the roles is the line between using the design, moving a change through, and building the machinery.

A user uses it. Anyone can set the inputs — by hand or as a CSV — run any row on them, save what the run returned and send it on, and look at a result somebody else saved without running anything. When a node is wrong, missing or unfinished, the person who knows the answer fills in that node's form and sends it. They get a preview of their change back, try it, and press Approve — or say what is still wrong.

A maintainer moves each change through. A form that arrives is taken in onto its own branch — checked, applied, tested — and its author is sent the preview. Their approval comes back as a file, and is recorded against exactly the build they tried. Approved changes are merged, and released to everyone when the maintainer chooses. Every step is one command.

A developer builds the machinery. A form that adds a relation needs code in the kernel; a check that fails for a reason not in the form needs a diagnosis; the tool's pages, pictures, checks and generators are designed and improved. All of it through the gate and a reviewed pull request.

Each role has its own guide — docs/roles/user.html, maintainer.html and developer.html — generated from this manual, so the three can never disagree with it.

Read a row explanation

answer firstA row's page opens with its answer first, then says it simply, then the real relation and its source, then where the simple version breaks. Every claim says whether it is sourced, derived or declared, and the depth switch chooses how much is shown.

A row's page answers four questions, in order.

What it is made of — the files in its folder, which one a person writes (node.toml, the sheet) and which ones are generated from it.

What it is joined to — the rows it reads, the rows that read it, and which customer targets it feeds.

What it says — the sheet itself, laid out the same way on every row: an Answer first box, then the row said simply, then the real thing — its relation and where that came from — then where the simple version breaks, and the wrong idea readers most often bring. Every claim is marked sourced, derived or declared, and every tab says whether it is an explanation, a reference or something to try. The de-risking tab says what the row rests on and why it changed. Beside the sheet is the node's form, for when what it says should change.

The picture — for the rows that have one, the figure the claim is argued from.

A grey row is seeded: its folder exists and nothing is specified in it yet. That is the normal state of most of the tree — the decomposition written down before anyone was asked to fill it — not a failure, and its form is how it gets filled. A row marked INACTIVE has a relation but nothing on its sheet saying where the relation came from, so it does not answer until a form supplies that and a developer applies it.

Set the inputs — the case how-to

answer firstEvery run is on one case: its inputs, set on the Inputs page or uploaded as a CSV and saved outside the repository. A file is shown before it is saved, refused whole if any row is bad, and carried over when the tool is updated.

There is one case, the multipayload design, and every run, sweep and figure in the tool is for it. What changes from one customer to the next, or from one sky to the next, is its inputs — never the tree. A customer is a set of values, not a folder, so a new customer is never a change to the design.

The Inputs tab lists all of them in two halves. Condition is what the design flies in: the orbit, the environment and the solar weather it is sized for. Customer is everything else — the payloads, the vehicle, the service and what it must deliver. Each shows the value it runs at, its default — the value declared on its own sheet — and the range it may move in.

Change values there and save them, or upload a CSV. A file is read and shown before anything is saved: what it sets, what that changes, and every row it refuses. A file with any refused row — a name that is not an input, a unit that is not the row's, a value outside the declared range — is not used at all, because keeping the good half would be a run on values nobody asked for. A blank value means the default, so a file only has to name what it changes.

The saved case is kept by the tool outside the repository — beside the reference data, in ~/.vleo/case/, or wherever VLEO_CASE points — so git never sees it. To keep a copy, or hand one to someone, download it; to put it back, upload it. The bar across the top always says how many inputs the saved case changes.

When the tool is updated, a case carries over. Every CSV the tool writes names the set of inputs it was written for, in a #! template line — keep it. When a release adds, retires or re-ranges inputs, a case written before is not refused: every value that still applies is carried, every new input runs at its default, and any value that can no longer be used — its input retired, or now outside its range — is set aside by name, with its value and why, rather than dropped. The saved case is carried over on its own the first time the updated tool reads it, and the file as it was is kept beside it; the Inputs page says what the update did until you keep the result. An old file you upload is carried over the same way, and shown before it is saved.

  1. Open every input of the case. The bar across the top has the same way in.

    look for download a blank template
  5. Upload a CSV. What it would change is shown first; nothing is saved until you say so.

Run a row, and ask “what if” how-to

answer firstRun any computed row on the case, or change an input first to ask what if. A run always says how many rows ran and names every one that was blocked.

Every computed row can be evaluated on the spot, on its own page or from the 4 The run tab.

A run is on the case — its saved inputs, see Set the inputs. The panel says so in a sentence, and under it lists every input the answer depends on, the most influential first, each with the value it will run at, which half of the case it is in, and where the value came from: the default, the saved case, or your edit.

Change one to ask a what-if. The edit is kept in this browser only — listed in the bar at the top, applied to every run and sweep until you reset it, and never written to a file. A computed row cannot be changed this way: its value would be recomputed from its inputs the moment it ran, so change one of the declared numbers it reads instead. When a what-if is worth keeping, save it to the case and every page runs on it from then on.

The result always says n ran, m blocked, and names every blocked row. A row with nothing in it does not quietly supply a default — it refuses, under its own name, and everything that needed it says so. That count is never hidden, because a number built partly on refusals is not the number it looks like. What unblocks such a row is its form, filled and applied — see Ask for a node to change.

Keep a result, send it, and see it again without running how-to

answer firstSave a run or a sweep as a result, and see it again later without running anything — or send its report page. A question already answered is not run again: the tool shows the saved answer and says so. A result keeps the node versions it rested on, and says when one of those beliefs has broken since.

A run is worth keeping when somebody will ask about it later. Save it and the tool keeps a folder: result.csv — every value the run returned with its unit, its credibility and what governs it, every row it blocked on and why, and every input it ran on — sweep.csv when it is a sweep, and report.html, the page to send. It is kept in ~/.vleo/results/ or wherever VLEO_RESULTS points — outside the repository, like the case.

A question already answered is not run again. Everything that decides an answer — the row, how much of the graph, every input, the engine, the tree and the reference data, and for a sweep what it moved and how — is one key. Press run or sweep on a question already kept and the saved answer is shown, with a line saying which result it came from and when; run again anyway runs it fresh. Saving the same question twice keeps it once. With VLEO_RESULTS on a shared folder, that includes questions a colleague answered. A change to the engine's code or to the tree is a different key, so an answer from before a correction is never shown for the corrected tool.

The Results tab lists every saved result and shows any of them as it was — nothing runs, so a result saved before a release reads exactly the same after it. Two results can be compared value by value, and the inputs that differ between them are listed first, because that is usually the answer.

A saved sweep is drawn again on the Results page from its saved points, with the same chart the run panel uses — hover, zoom and copy the numbers — and nothing runs.

To send one, download its report: one HTML page that reads without the tool, draws the sweep, and carries the CSVs inside it, so uploading the report gives the result back whole. The CSV opens in any spreadsheet. A result somebody sent you is uploaded the same way: its report, or its result.csv with its sweep.csv.

Results are kept in tiers. Every value for 30 days — VLEO_KEEP_DAYS sets how many — and the summary for good: when the tool starts, an older result is thinned to the inputs it ran on, its answer and what could not run, and says so on its page and in its report. The rest is one run away, because the same engine on the same inputs gives the same answer; a thinned result is not offered as a kept answer, so asking its question again runs it. Pin a result to keep every value of it for good. A shared folder named by VLEO_RESULTS is kept whole unless VLEO_KEEP_DAYS is set too.

A result's inputs can become the case. That puts every input back to what the result ran on — the way to reproduce it, or to carry on from it. It is checked like any other case, and refused whole if a release has since retired or re-ranged something it sets.

  1. After a run, give the result a name if you like, then keep it.
    look for save this result
  2. Every result kept on this machine. Open one to see it; nothing runs.
    look for Results
  3. Put two side by side: what moved, and the inputs that differ.
    look for compare with
  4. Send it: the CSV for a spreadsheet, or the report for someone without the tool.
    look for download report
  5. Keep a result somebody sent — its CSV or its report.
    look for upload a result…
  6. Run on exactly what it ran on.
    look for use its inputs as the case
  7. After a sweep, keep it the same way: the run at the case and the line across the range, together.
    look for save this sweep

Ask for a node to change, or for a new one how-to

answer firstTo change a node, or ask for a new one, download its form, fill it anywhere and send it to the developers. If the change moves what the node computes, the form also says why: which belief broke, what was tested and what we now know.

Every node has a form: one self-contained HTML file that needs no connection and nothing installed. It explains itself, asks every question the node's sheet answers with why each is asked, shows what the node reads and feeds and the known-good values that already hold it, lists every row it could read, and saves a filled copy of itself. Send it to whoever should say what the node is — a payload team, a customer's engineer, a reviewer. It can be filled by hand, or given to an assistant: the content is a plain block of text near the end of the file.

For a node the design does not have yet, download the form for a new node. It also asks where the node goes — its parent, and so its layer — and what kind of row it is.

What it reads is its interface. Every input names a row that exists, and the form says, as you type, what that row is and its quantity. A developer's first check is exactly this: that every input is a row, of the quantity the node expects.

Why it is changing. A change to what the node computes — an input, the output, the model, the maths, the algorithm, how it is drawn — also says which belief broke: what we believed, what we tested, what we now know, what changes, and what the node rests on now. The form says as you type which decisions your changes move and what is still to answer; without it the developers apply only your wording. Wording alone needs none of it.

Send the filled file to the developers. This page can check it first — what it would change in the node, every interface it declares, and what cannot be applied: a field the design changed since the form was made is a conflict, never overwritten, and a relation an assistant supplied is refused, because mathematics is derived by a person. Nothing is written here. Known-good values in a form are passed to whoever records fixtures; they are never written from a form.

  1. Every form in one place: the inputs, results, and each node's form.
    look for Forms
  2. Or from a node's own page: in the sheet, open the form tab.
    look for the node form — fill it anywhere
  3. Download it and send it to whoever should fill it.
    look for download the node form
  4. For a node that does not exist yet.
    look for download the form for a new node
  5. When it comes back, check it: what it would change, every interface, and what it cannot. Nothing is written.
    look for check a filled form…
  6. A lesson is written the same way: its form, filled anywhere, checked as you type, sent back.

Give the method, your code and your test cases how-to

answer firstIn a node's form, write the relation once more as a method — a few lines in a small fixed language — paste the code you wrote and tested, and give at least three cases your code answered and one it refuses. The form runs your method on your cases as you type and shows any that disagree, before you send it.

A node's relation arrives three ways, and each checks the other two. Your code — MATLAB, Python, C, anything — produced your test cases. The method says the same relation in the method language (docs/PSEUDOCODE.md), which the tool can check for units and run. The code the tool ships is generated from the method. All three must give your answers, so a mistake in any one of them shows up as a case that disagrees.

The method. It reads the node's inputs by their names, gives every number its unit in brackets — 250 [km], 30 [deg] — and ends every path with return (the answer) or refuse (why it will not answer). The form checks the units as you type: adding a length to a time, taking the logarithm of a length, or returning the wrong quantity is shown on the line it happens.

Your cases. Each is a set of inputs, in SI, and the answer your code gave for them, with how close counts. At least three answers and one case the node must refuse — the refusal shows the method says no where your code says no. The method's value appears beside yours only after you have typed yours, so the tool is never where your answer came from.

Your code and its test are pasted whole, with what ran them. They are kept with the node so the cases can be produced again and a reviewer can read where the numbers came from.

Flight software that implements the node can be kept in the same form, each file with its test and its last result. It is stored beside the relation, not built by the tool.

Every question has Show the example beside it: the same question answered for one worked node, marked illustrative.

  1. Open the node's form and find The method. Read The method language on one page if it is your first.
  2. Write the method, then fill Your code: the code, its language, the function that is this node, and the test code that ran it.
  3. Add your test cases — three or more with the answer your code gave, and one it refuses — and watch Check: the method against your cases until it says Sound.
  4. Say in Why it is changing what adding the method tested, save a filled copy and send it.

Try the preview of your change, and approve it how-to

answer firstAfter you send a form, you get a preview of the tool with your change in it. Install it, try the nodes it names, and press Approve only when they give what you expect; send back the small file it saves. Nothing reaches everyone else until you do.

A preview is the tool built from your form, before the change is approved. It is the same one-file package as a release, and it says so on every view: an orange PREVIEW banner names your change, the nodes it touches and the build. Install it exactly like a release, over the one you have — your inputs and results are kept, and the next release replaces the preview.

Open each node the banner names, read its page, run it, move its inputs, and check the answers against your own. If anything is wrong, do not approve — tell the maintainer what, and you will get a new preview. When it is right, press Approve this preview…, tick that you ran it, and save the file. Send that file back the way you sent the form.

The file is for this build and no other: if anything changes after you approve, you are sent a new preview to approve.

  1. Install the preview package you were sent, then start it.
    python -m pip install <preview>.whl
    changes files
    installs the preview over the tool you have; your case and results are kept
  2. The banner names the nodes your change touches — open each, run it, check it.
    look for not a release
  3. When every one is right, approve — tick that you ran it — and save the file to send back.
    look for Approve this preview…
  4. The file it saves is your approval of this exact build.

Why a node changes — its beliefs, versions and risks explanation

answer firstA node changes only because a belief it rested on broke, and every change records what we believed, what we tested, what we now know and what changed. The risk-register rows of the management layer conclude, from every node's record, how that work has moved the programme's risks.

Every decision in the design rests on a belief — that this relation holds here, that this input is the one that matters, that this picture shows what it claims. A node changes only when one of those beliefs breaks: somebody tested it and learned otherwise. So a node's page has a de-risking tab. It says what the node rests on now and what would break it, then every version before it, newest first: what we believed, what we tested, what we now know, what it cost, what changed, and which risks that moved.

sw_central_expectation — the centre of the F10.7 design value — carries its real history as the worked example: three versions, each replaced because a test showed its belief did not hold.

The conclusion is drawn in the management layer. A risk is registered once, on one of the four risk-register rows — technical, schedule, supply, regulatory — and moved only by node versions. Each of those rows' pages lists its risks, where each started and where it stands now, and every version across the tree that moved it. That is how the work below, taken together, has de-risked the programme; docs/DERISK_NARRATIVE.md is the same thing as a document, and docs/derisking.csv as a spreadsheet.

A saved result keeps the versions it rested on. When one of those rows has moved on since, the result says so beside its number.

How deep a page goes is yours to choose. The switch at the top — Learn, Read, Expert — shows the same pages at three depths: Learn keeps every step and asks you to predict before you run; Read shows the answer, the plain words and the real thing; Expert keeps the answer, the relation, the limits and the reference. How every page is laid out, and why, is in docs/EXPLAINING.md.

  1. Choose how deep the pages go. Learn adds a prediction to make before each run.
    look for Learn
  2. Open a row and its de-risking tab: what it rests on now, and every version before it.
  3. Open a risk-register row under the management layer's risk register: its risks, and what the work below has done to them.
    look for What the work below has done to them

What the browser will not do reference

answer firstThe browser never changes the design. Each thing it will not do has a place it is done instead, and for a team that place is almost always a node's form.

The browser never changes the design: not a field, not a row, not the tree. That is not to keep anybody out. A change to the design has to be checked against every row that reads it, implemented, given evidence, and released so that everyone runs the same thing — and a change typed into one copy of the tool does none of that. So each one below has a place it is done instead, and for a team that place is almost always a form.

The fields a node form does not carry at all — the ones that move a row in the tree or change who owns it — are listed live under Reference, each with its reason.

Run, change an input, sweep, keep the result how-to

answer firstRun a row on the case, on a CSV of your own or on the declared defaults, change a declared input with --set, sweep one, and keep a run as a result file.

The examples use the storm row sw_ap_design: what daily Ap is this design built to survive? It reads one declared number, the storm level designed for, and turns it into the Ap that level bounds.

A run prints the answer, its credibility — the weakest of eight factors, named — and n ran, m blocked with every blocked row named. The chain hash identifies that exact number: the engine, the tree and every input that reached it. Two runs with the same chain are the same run, so it is the thing to quote.

A run is on the case: the saved one — the same file the browser saves — or, with --inputs, a CSV of your own, or with --defaults every input at its declared value. The first lines of a run say which. vleo inputs prints the case as a CSV to fill in; a blank value means the default, and a file with any row that cannot be applied is refused whole, each bad row named. A file written by an older version of the tool — its #! template line says so — is carried over instead, and vleo inputs --inputs old.csv writes it out in the current template, with every value it could not carry kept as a #! set-aside line. The order is fixed: each row's declared value, then the case's, then --set.

--set only changes a declared number — never a computed one, which would be overwritten the moment it was evaluated — and it never writes the sheet.

--save writes the run as a result file where you say; --keep keeps it in the results folder the browser's Results page shows, once. A question already kept there is shown from its saved result instead of run — the first line says so — and --again runs it anyway. vleo result shows a result again, from its folder, its CSV or its report, without running anything.

Two of the steps use a closure, l3_solar_ach_01: the room the sustained F10.7 requirement has left once the design flux is taken from it. The launch date is one of the declared numbers behind it, and a time is given in seconds.

  1. Run a row and everything it needs.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design
    safe to run — only reads
    it says: Ap_design = 132
  2. What if the design were built for a weaker storm? Change the declared number it reads.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --set sw_storm_design_level=2
    safe to run — only reads
    it says: Ap_design = 80
  3. A computed row cannot be set, and the tool says which declared numbers to set instead.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --set sw_ap_design=100
    shows a refusal — it is meant to fail here
    it says: is computed from its inputs
  4. Print the case as a CSV — every input, its unit, default and range. Fill in value and keep the file anywhere.
    cargo run -p vleo-cli --bin vleo -- inputs --defaults
    safe to run — only reads
    it says: group,id,name,value,unit,default,min,max
  5. Run on a case file. This one designs for a G2 storm and leaves every other input at its default.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --inputs cases/examples/storm_level_2.csv
    safe to run — only reads
    it says: Ap_design = 80
  6. A file from an older version of the tool is carried over, not refused: what still applies runs, new inputs take their defaults, and a value that cannot be used is set aside by name.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --inputs cases/examples/from_an_older_tool.csv
    safe to run — only reads
    it says: carried over from an older version
  7. Or on the declared defaults, whatever case is saved.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --defaults
    safe to run — only reads
    it says: Ap_design = 132
  8. Keep the run as a result file — every value, every input it ran on.
    cargo run -p vleo-cli --bin vleo -- run sw_ap_design --inputs cases/examples/storm_level_2.csv --save my-result.csv

When something goes wrong reference

answer firstThe usual failures, each with what it means and what to do. Almost every refusal names the field and the rule, and that line is usually the whole answer.

The tool will not start: nothing was free. It tries sixteen ports from 7777 upward. Something else is holding them — often an earlier copy of the tool. Stop that one, or set VLEO_PORT to start somewhere else.

An uploaded case or result is refused. Every refused row is named, with why. A case is all or nothing, so correct the named rows and upload it again. A file from an older release is carried over rather than refused; one the tool did not write — no #! result line — is not a result at all.

A form's check shows a conflict. Somebody changed that field in the design after the form was made. Nothing is overwritten: download the node's form again, carry the answer across, and send the new one.

A form's check says an interface does not connect. The input names a row that does not exist, or one of a different quantity. The line says which, and what the row it names actually is.

The checks refuse a row. Each failure names the field and the rule. Read that line before anything else; it is almost always the whole answer.

A row prints INACTIVE and does not answer. Its relation is written but nobody has derived it: the sheet has no [theory] block saying why it is this relation. That is a person's work, supplied through the node's form, never something to work around — and every row that reads it is blocked, by name, until it is done. active lists each such row and how many rows wait on it.

A sweep answers no point. Every point is still recorded, with why: blocked when a row on its chain does not answer, or the bound and its reason when the value is outside the declared range of the row being swept.

A command warns that the hooks are not wired. Run setup once in this checkout.

The commit hook refuses a message. It must read type(scope): a sentence, and tools/commit_message.py --types prints every type and scope it accepts.

A number looks wrong. Run the row in the terminal, read its credibility line and which factor governs it, and look at the chain behind this number — every value that reached it, with each one's own credibility. If the design is what is wrong, that is a form.

  1. Start the tool on another port.
    VLEO_PORT=8080 cargo run --release -p vleo-daemon
    starts the tool
  2. Every row that is written but does not answer, and how many rows wait on each.
    cargo run -p xtask -- active
    safe to run — only reads
    it says: undefined — the relation is stated and never derived
