answer first declared · the repository's rules

You write what the routine cannot: a new relation in the kernel, a filled HOLE, a diagnosis of a failing check — and you improve the tool itself: its checks, generators, pages and pictures. Everything goes through the gate and a pull request reviewed by the number of people CONTRIBUTING sets.

your role, in four steps
1

Say it simply

If the maintainer runs the print shop, you build and repair the presses. You do not decide what is printed — that comes from the forms — but you make sure the presses print it exactly, and you check them against pages you did not print yourself: the fixtures.

illustrative — an analogy, see step 3 for where it stops

2

Now the real thing

You do

  • Build a node from its method with build-node; for what the method language cannot say, fill its HOLEs from kernel relations.
  • Keep the method language, its checker and its translator one reviewed change, and rebuild the form's checker with method-wasm.
  • Add a relation to vleo-core::physics when a form needs one — a reviewed change every node reads.
  • Diagnose a check that fails for a reason outside the form.
  • Improve the tool: its pages and pictures, the loop's commands, the checks, the release pipeline.
  • Keep this manual true: every command, route and label it names is tested against the tool.
3

Where the simple picture breaks

‘You do not decide what is printed’ stops at the tool itself: its pages, pictures, checks and generators are yours to design — reviewed like any code, by two people where CONTRIBUTING says so.

You never

  • Supply a relation — the physics comes from a node's owner, through their form.
  • Take an expected value from the code under test.
  • Edit a generated file outside a numbered HOLE.
  • Put a formula anywhere but vleo-core::physics, or call the standard library's transcendentals in the kernel.
  • Widen a tolerance to get green.
4

Try it · predict first

A node's test fails after a form changed its input range. The fixture's expected value is 0.8% off and the tolerance is 0.5%. What do you change?

Say your answer, then open

Neither the tolerance nor the fixture. A fixture disagreement is a physics question: it goes to the node's owner, with the number. If the fixture is wrong, its source says so and a person corrects it; if the code is wrong, you fix the code.

common wrong idea

“The tests pass, so the node is right.”

Tests compare the code with values from outside it — the fixtures. A test whose expected value came from the code only proves the code agrees with itself, which is why the gate refuses one.

In the browser

Everything a team using the tool does: read the design, set the inputs, run, keep what a run returned, and ask for a node to change. Nothing in the browser changes the design. What you set and what you keep are yours and stay on your machine; what the design is changes only through a node's form, which the developers check, apply and release.

Open the tool how-to

answer firstStart the tool with one command and open the address it prints. It never writes the repository: what you keep — the case and your results — stays on your machine under ~/.vleo.

The tool is one program on your own machine. It serves this page and computes every number on it, from one address, with no internet and no database. It listens on 127.0.0.1 only, so nobody else on the network can reach it.

It never writes the repository. The two things you can keep — the case you run on and the results you save — are kept outside it, under ~/.vleo/, so a checkout stays exactly as it was released and git status is empty however much you use the tool. The status card at the top of this manual says where this copy keeps them.

  1. Start it. It prints the address it got — the first free port from 7777 upward.
    cargo run --release -p vleo-daemon
    starts the tool
  2. Open the address it printed, normally http://127.0.0.1:7777.
  3. In a Codespace there is nothing to type: the tool is already running and port 7777 opens as a preview.
  4. Without a repository, the tool comes two ways. The one file for every laptop: python -m pip install vleo-<version>-py3-none-any.whl once, then python -m vleo — it runs inside Python, so Windows has no new program to stop. Or the desktop app: on Windows unzip the kit and double-click VLEO Design Tool.exe; on a Mac unzip VLEO Design Tool and open it; on Linux run ./vleo-app. Either opens the page itself; START_HERE.md says the rest.

Who does what explanation

answer firstThree roles around one loop. A user uses the tool and, when a node is wrong or missing, fills its form, tries the preview of the change and approves it. A maintainer takes each form in, sends the preview, records the approval and releases. A developer writes what that routine cannot: code, checks, the tool itself.

The line between the roles is the line between using the design, moving a change through, and building the machinery.

A user uses it. Anyone can set the inputs — by hand or as a CSV — run any row on them, save what the run returned and send it on, and look at a result somebody else saved without running anything. When a node is wrong, missing or unfinished, the person who knows the answer fills in that node's form and sends it. They get a preview of their change back, try it, and press Approve — or say what is still wrong.

A maintainer moves each change through. A form that arrives is taken in onto its own branch — checked, applied, tested — and its author is sent the preview. Their approval comes back as a file, and is recorded against exactly the build they tried. Approved changes are merged, and released to everyone when the maintainer chooses. Every step is one command.

A developer builds the machinery. A form that adds a relation needs code in the kernel; a check that fails for a reason not in the form needs a diagnosis; the tool's pages, pictures, checks and generators are designed and improved. All of it through the gate and a reviewed pull request.

Each role has its own guide — docs/roles/user.html, maintainer.html and developer.html — generated from this manual, so the three can never disagree with it.

What the browser will not do reference

answer firstThe browser never changes the design. Each thing it will not do has a place it is done instead, and for a team that place is almost always a node's form.

The browser never changes the design: not a field, not a row, not the tree. That is not to keep anybody out. A change to the design has to be checked against every row that reads it, implemented, given evidence, and released so that everyone runs the same thing — and a change typed into one copy of the tool does none of that. So each one below has a place it is done instead, and for a team that place is almost always a form.

The fields a node form does not carry at all — the ones that move a row in the tree or change who owns it — are listed live under Reference, each with its reason.

Paste these from the top of the repository. Set up a copy how-to

answer firstInstall Rust, clone, wire the hooks once and fill the reference-data store once. Then the gate and the tests are the one command that must be green.

The only thing to install is Rust; the exact version is pinned in rust-toolchain.toml and fetched on first use. There is no database and no service.

setup points git at the project's own hooks so the commit-message rule runs before a bad message ever leaves your machine. Git will not do this on its own, because a hook that ran just because it was cloned would be a way to run anybody's code.

Every command here is written out in full. Two shorter forms work too: cargo xtask … for cargo run -p xtask -- …, and cargo vleo … for cargo run -p vleo-cli --bin vleo -- ….

  1. Get the repository.
    git clone https://github.com/AmanRai0603/VLEO_SIMULATOR && cd VLEO_SIMULATOR
    changes files
    creates a new checkout in the current directory
  2. Wire the hooks, once per checkout.
    cargo run -p xtask -- setup
    changes files
    sets core.hooksPath in this checkout's git configuration
  3. Fill the local store of reference data, once. It lives in your home directory, outside the checkout, so it never makes the working tree dirty.
    cargo run -p vleo-cli --bin vleo -- data sync
    changes files
    writes the reference-data store under $HOME/.vleo, or wherever VLEO_DATA points
  4. Prove the copy works. This is the one command that must be green before anything is pushed.
    cargo run -p xtask -- gate && cargo test
    the pipeline runs this too
  5. The short form works the same way.
    cargo xtask status
    safe to run — only reads
    it says: KPI closures declared

Take in a node form — check it first how-to

answer firstA developer's first act on a filled form is the checker, which writes nothing: what it would change, every interface it declares, what cannot be applied, and whether its reason is complete. Then --apply writes it as one edit, or not at all.

Every change to the design arrives as a node's form, filled by whoever knew the answer. A developer's first act on one is to check it, and nothing is written by checking. xtask intake reads the filled file and says, field by field, what it would change in the node's node.toml, against three versions: the node when the form was made, what the filler made of it, and the node now — so a change made in the repository meanwhile is a conflict, not overwritten. It checks every interface the form declares: each input must be a row that exists, or a named output of one, of the quantity the node expects. A relation an assistant supplied is refused, and so is a numbered step removed from the middle, because each number is a hole holding somebody's Rust.

A form for a new node says where it goes. Intake checks that the id is free and the parent is a group, and on --apply builds the folder in its place in the tree — on the shape of a sibling of the same kind — then writes the form into it and gates the whole tree, since a new row changes what the tree connects. Anything the form left blank is listed as still open.

--apply writes as one edit — regenerate, gate, and put everything back if the gate refuses — with your name on any relation it changes. It refuses while anything is blocked unless you add --partial. Known-good values in the form are printed as [[fixture]] blocks for whoever records fixtures; they are never written by intake. A filled seeded row is then published, which is what generates its code — see Implement a node.

  1. A node's form, to send out. With --out <file> it is written to a file.
    cargo run -p xtask -- form sw_ap_design
    safe to run — only reads
    it says: vleo-node-form/1
  2. The form for a node the design does not have yet.
    cargo run -p xtask -- form --new
    safe to run — only reads
    it says: A new node
  3. Check a filled form — this one changes the note, adds an assumption and supplies a known value.
    cargo run -p xtask -- intake docs/examples/sw_ap_design.node-form.html
    safe to run — only reads
    it says: can be applied
  4. Check a filled form for a new node: where it goes, what it would hold, and each interface it declares.
    cargo run -p xtask -- intake docs/examples/new-node.node-form.html
    safe to run — only reads
    it says: connects
  5. Apply it: written, regenerated and gated as one edit, or not at all. Then read git diff.
    cargo run -p xtask -- intake docs/examples/sw_ap_design.node-form.html --apply
    changes files
    it writes the node's sheet — or builds a new node's folder — and regenerates, which is a change to the repository to review and commit

Implement a node — the developer's loop how-to

answer firstAfter a form is applied: publish the row so its code is generated, write the Rust in each numbered slot, add evidence from outside this code, and check it. Every step names exactly what is still open.

A row is a folder, and only node.toml in it is written by hand — by a form's intake, or in your editor. Every other file is generated from it; an edit anywhere else is thrown away the next time the row is regenerated, and the checks catch it before then.

The loop after a form is applied: publish the row so its code is generated, write the few lines of Rust in each numbered slot, give it evidence from outside this code, check it, and ask whether a person should look yet. Every step names exactly what is still open, so there is never a guess about what is next.

Any assistant may help write a slot. fill takes the body as text, and --by and --model record who wrote it and with what, so a significant slot written twice by different models can be compared. What no assistant may supply is the relation itself — that comes from the form, and a person's name goes against it. Commit naming whoever filled the form.

  1. Ask what is still open, and what goes wrong without each answer.
    cargo run -p xtask -- declare sw_ap_design
    safe to run — only reads
    it says: ready to generate
  2. Publish a filled seeded row: its model, contract and evidence are generated and its slots can be written. It refuses, naming every reason, while the row is not ready.
    cargo run -p xtask -- publish <row>
    changes files
    moves the row to published and generates its code
  3. Write the Rust for one numbered slot. It goes in as text, never by opening the generated file; the tool refuses a body that would reach outside its slot.
    cargo run -p xtask -- fill <row> --hole <n> --body - --by "Your Name" --model <model>
    changes files
    splices a body into the row's generated model.rs and records who wrote it
  4. Add evidence to fixtures.toml: values from a paper, a measurement or a trusted tool — including the known values a form supplied. An expected value may never come from the code under test, and the checks refuse one marked as if it did.
  5. Generate the row's other files from its sheet. On a row that is already up to date, nothing is written.
    cargo run -p xtask -- docs sw_ap_design
    safe to run — only reads
    it says: 0 artefact(s) written
  6. Check it. Every failure names the field and the rule.
    cargo run -p xtask -- gate sw_ap_design
    safe to run — only reads
    it says: 0 node check failure(s)
  7. Ask whether a person should look yet. It stops at the first thing a machine could have found.
    cargo run -p xtask -- ready sw_ap_design
    safe to run — only reads
  8. List the relations nobody has put their name against yet, grouped by who owns them.
    cargo run -p xtask -- confirm --list solar
    safe to run — only reads
  9. Put your name against one relation, after reading it against its source. There is deliberately no way to do many at once.
    cargo run -p xtask -- confirm <row> --by "Your Name"
    changes files
    writes your name and today's date against the relation on the row's sheet

Record why it changed, and cut a release how-to

answer firstEvery applied change appends a version to its node; the narrative is regenerated from all of them; and a release stamps every unreleased version with the release that ships it.

A form that moves what a node computes carries its reason — what we believed, what we tested, what we now know, what changed, and what the node rests on now. Intake checks the record with everything else: without it, only the form's wording is applied and every decision is withheld, by name; with it, the changes go in and a [[version]] is appended to the sheet, numbered and marked next. The kinds of decision it moved are read off what the form changed, never asked. A risk move names a risk registered on a risk-register row, or the record is refused.

The narrative is generated from every node's record: docs/DERISK_NARRATIVE.md to read and docs/derisking.csv for a spreadsheet, in the columns of the quarterly de-risking narrative. The pipeline regenerates both and fails on a difference.

A release names the beliefs it ships. xtask release <version> stamps every next with the release, sets the workspace version and regenerates; the release pipeline runs release <version> --check and refuses while any version is unstamped. Why, and the rules, are in docs/DERISKING.md.

  1. Regenerate the narrative. On a tree whose narrative is committed, nothing is written.
    cargo run -p xtask -- derisk
    safe to run — only reads
    it says: nothing to write
  2. A saved result says which node versions it rests on — and, if one has moved on since, that a belief it rested on has broken.
    cargo run -p vleo-cli --bin vleo -- result docs/examples/sw_ap_design.result.csv
    safe to run — only reads
    it says: a saved result
  3. Cut a release: every unreleased version stamped, the workspace version set, everything regenerated. Then gate, commit and tag.
    cargo run -p xtask -- release <version>
    changes files
    stamps release on every unreleased node version, sets the version in Cargo.toml and Cargo.lock, and regenerates

Share the tool with the team how-to

answer firstThe team gets the tool, not the repository: one Python package for every laptop, or a kit per platform — the programs beside exactly the files they read, with START_HERE.md on top. They use it and send back node forms; you apply them, release, and share the next version.

The daemon reads the web face, the tree and every node's page at run time, so the programs alone do not run. xtask kit puts them beside exactly those files — no git history, no generators, no kernel source — in dist/vleo-<version>/, with START_HERE.md (from docs/TEAM_GUIDE.md) and VERSION — and start.sh off Windows; the desktop app ships beside the daemon, on Windows as VLEO Design Tool.exe, with its icon and no console window, and xtask app makes the Mac's VLEO Design Tool.app from a Mac kit. Zip it and share it. A kit runs on the platform that built it; the release pipeline builds one for Linux, macOS and Windows, and one Python package, vleo-<version>-py3-none-any.whl, that carries the engine for every system and runs with python -m vleo — no new program for Windows or an antivirus to question. The team's case and results live under ~/.vleo/, outside both, so the next version replaces them without losing either. The whole loop is in docs/SHARING.md.

  1. Build the two programs the kit carries.
    cargo build --release -p vleo-daemon -p vleo-cli
    safe to run — only reads
  2. Assemble the kit in dist/vleo-<version>/ — then zip that folder and share it.
    cargo run -p xtask -- kit
    changes files
    writes dist/vleo-<version>/, which git ignores

The method language and the form's checker how-to

answer firstThe method language is one module, vleo_sheet::method. Every node form carries it compiled to WebAssembly as web/method.wasm.gz; after changing the language, rebuild that file with method-wasm and commit it with its stamp.

The gate, take, intake and the node form all call vleo_sheet::method — the form through web/method.wasm.gz, which xtask method-wasm builds from crates/vleo-method-wasm. A test refuses a checkout whose checker sources have moved on from the committed file, so a form can never check by older rules than the gate. A form reads the file from beside the tree when it is made; no program carries it built in, because compressed WebAssembly inside a program is what Chrome blocked in the first 0.3.0 Windows kit, and the release refuses a program that does. docs/PSEUDOCODE.md is written by xtask docs from the same tables the checker reads. Changing what a method means is a reviewed change to every node that has one.

  1. Rebuild the checker every form carries, after changing the language.
    cargo run -p xtask -- method-wasm
    changes files
    builds crates/vleo-method-wasm for wasm32 and writes web/method.wasm.gz and its stamp
  2. Or only ask whether it is current.
    cargo run -p xtask -- method-wasm --check
    safe to run — only reads
    compares the fingerprint of the checker's sources with the one recorded beside web/method.wasm.gz

When the method language cannot say it how-to

answer firstA node the method language cannot express — a set of answers, a solver that stops when it converges — keeps hand-written holes. A developer writes them, with an assistant if they like, and the author's cases still decide.

The language is closed on purpose: every construct has one translation, so the translator needs no judgement. What it cannot express goes to the existing route: fill splices each hole body, --by and --model record who wrote it, and a significant node's holes are written twice by different model families and compared with differential. An assistant here is a worker, never a judge: acceptance is only ever the author's cases, the fixtures, the mutation check and the gate — and no assistant supplies the relation, the method or a case.

When the language grows a construct, it grows in crates/vleo-sheet/src/method.rs: the grammar, the checker, the interpreter and the translation together, one reviewed change, followed by method-wasm so every form checks by the new rules.

  1. Build a node from its method by hand, stage by stage.
    cargo run -p xtask -- build-node <node>
    changes files
    translates, tests, reruns, mutates and only then checks the interface; stops at the first stage that fails

Is the evidence real? how-to

answer firstTwo commands ask whether the tests are worth anything: every fixture declaration is sound, and a perturbed answer is caught by the row's own tests.

A test that passes against a broken implementation is not testing anything. Two commands ask that question directly.

  1. Run one subsystem's tests, including every row's fixtures.
    cargo test -p vleo-mod-solar
    safe to run — only reads
  2. Check every fixture declaration in the tree is sound — its source is outside the code and its tolerance is positive. It does not execute them; cargo test does.
    cargo run -p vleo-cli --bin vleo -- selftest
    safe to run — only reads
    it says: fixture declarations sound
  3. Perturb a row's answer slightly and require its own tests to notice. The row is put back afterwards.
    cargo run -p xtask -- mutate sw_ap_design
    safe to run — only reads
    it says: mutant(s) killed

Before you push, and how to release how-to

answer firstRun the pipeline's checks before pushing: the gate and every test first, then formatting, lints, the assembly validations and the panels. A change from a form names who filled it.

The pipeline runs all of these on every push; running them first saves a round trip. The first is the one that must be green.

Commit messages read type(scope): a sentence saying what changed. The hook installed by setup refuses anything else before it leaves your machine, and the pipeline runs the same rule. A change that came from a form names who filled it. How many reviewers a change needs is in CONTRIBUTING.md.

Once merged, the change reaches the team in the next release: they update, and their saved case carries over on its own — see Set the inputs.

  1. The checks and every test.
    cargo run -p xtask -- gate && cargo test
    the pipeline runs this too
  2. Formatting.
    cargo fmt --all -- --check
    the pipeline runs this too
  3. Lints, with every warning an error.
    cargo clippy --workspace --all-targets -- -D warnings
    the pipeline runs this too
  4. The assembly validations — the checks that can only be asked with the whole tree in view.
    cargo run -p xtask -- assemble
    the pipeline runs this too
  5. The panels render and respond, and the ones checked on pixels match their stored pictures, light and dark. A stored picture is only as good as whoever looked at it: panels/REVIEW.md says who has signed each, and which are still waiting.
    python3 tools/panel_check.py
    the pipeline runs this too
  6. The commit types and every valid scope.
    python3 tools/commit_message.py --types
    safe to run — only reads
    it says: scopes:

Reference data how-to

answer firstReference data arrives by an explicit sync as published, hashed sets; a run has verified data on disk or refuses to start.

The engine never fetches anything while it runs. Reference data arrives by an explicit sync beforehand, as published sets with a manifest, a licence term and a hash — so a run either has verified data on disk or refuses to start.

  1. What is in your local store, and whether it has gone stale.
    cargo run -p vleo-cli --bin vleo -- data list
    safe to run — only reads
    it says: verified
  2. Re-check every hash in the store.
    cargo run -p vleo-cli --bin vleo -- data verify
    safe to run — only reads
  3. Re-check every published set in the repository.
    cargo run -p xtask -- bundle verify
    safe to run — only reads
    it says: 0 refused
  4. Publish a new set. This cannot be undone, by design — publishing twice from the same input gives the same hash, which is what makes verifying mean anything.
    cargo run -p xtask -- bundle publish <dir>
    changes files
    writes a new bundle and its manifest under bundles/, permanently

Regenerate what is generated how-to

answer firstGenerated files are regenerated from their sources and committed; the pipeline fails if they differ from what the sources give.

Some files are written by the tool from others and never by hand. The pipeline regenerates each one and fails if the result differs from what was committed, so after changing what they are made from, regenerate and commit the result.

  1. Every row's generated files, from its sheet.
    cargo run -p xtask -- docs
    changes files
    rewrites any row's generated files whose sheet has changed
  2. CODEOWNERS, from the layer files — who reviews which rows.
    cargo run -p xtask -- codeowners
    changes files
    rewrites CODEOWNERS
  3. docs/VARIABLES.md — every variable, its unit, its range and the reason for each bound.
    cargo run -p xtask -- variables
    changes files
    rewrites docs/VARIABLES.md

Talk to the running tool from a script reference

answer firstEverything the page does is plain HTTP to the daemon, in SI units, and a script can do the same. No route writes the repository.

Everything the page does, it does over plain HTTP to the daemon, and so can a script. Every value crossing that boundary is in SI units; a face converts for display, never for transport. The full list of routes is under Reference. No route writes the repository: the only things a request can save are the case and results, both kept outside it.

  1. The engine's identity.
    curl -s http://127.0.0.1:7777/v1/version
    asks the running tool
    it says: kernel
  2. Run a row; the answer comes back as JSON.
    curl -s 'http://127.0.0.1:7777/v1/run?node=sw_ap_design'
    asks the running tool
    it says: sw_ap_design
  3. The results kept on this machine, newest first, and where they are kept.
    curl -s http://127.0.0.1:7777/v1/results
    asks the running tool
    it says: results
  4. This manual, as the page receives it.
    curl -s http://127.0.0.1:7777/v1/manual
    asks the running tool
    it says: layers

When something goes wrong reference

answer firstThe usual failures, each with what it means and what to do. Almost every refusal names the field and the rule, and that line is usually the whole answer.

The tool will not start: nothing was free. It tries sixteen ports from 7777 upward. Something else is holding them — often an earlier copy of the tool. Stop that one, or set VLEO_PORT to start somewhere else.

An uploaded case or result is refused. Every refused row is named, with why. A case is all or nothing, so correct the named rows and upload it again. A file from an older release is carried over rather than refused; one the tool did not write — no #! result line — is not a result at all.

A form's check shows a conflict. Somebody changed that field in the design after the form was made. Nothing is overwritten: download the node's form again, carry the answer across, and send the new one.

A form's check says an interface does not connect. The input names a row that does not exist, or one of a different quantity. The line says which, and what the row it names actually is.

The checks refuse a row. Each failure names the field and the rule. Read that line before anything else; it is almost always the whole answer.

A row prints INACTIVE and does not answer. Its relation is written but nobody has derived it: the sheet has no [theory] block saying why it is this relation. That is a person's work, supplied through the node's form, never something to work around — and every row that reads it is blocked, by name, until it is done. active lists each such row and how many rows wait on it.

A sweep answers no point. Every point is still recorded, with why: blocked when a row on its chain does not answer, or the bound and its reason when the value is outside the declared range of the row being swept.

A command warns that the hooks are not wired. Run setup once in this checkout.

The commit hook refuses a message. It must read type(scope): a sentence, and tools/commit_message.py --types prints every type and scope it accepts.

A number looks wrong. Run the row in the terminal, read its credibility line and which factor governs it, and look at the chain behind this number — every value that reached it, with each one's own credibility. If the design is what is wrong, that is a form.

  1. Start the tool on another port.
    VLEO_PORT=8080 cargo run --release -p vleo-daemon

The shape of it explanation

answer firstOne kernel computes every number; everything else is arranged in rings that depend inward only. A row is one folder, and only its node.toml is written by hand.

One kernel computes every number. Everything else is arranged in rings that depend inward only: quantities and portable maths (vleo-units), then the kernel of physics and relations (vleo-core), then transport (vleo-bus), then one crate per subsystem of rows (vleo-mod-*), then the faces — the browser daemon, the command line, and the Python, WebAssembly and C bindings. xtask graph checks every dependency points inward.

Every formula lives in vleo-core::physics and nowhere else. A row composes relations from there in a few lines; it never defines one of its own.

The tree is layers of rows. Layer 1 is the programme's view, layer 2 the system's, layer 3 the subsystems', and layer 4 is a run. Each subsystem reaches the layer above through exactly one interface row, so where did this number come from is answered by walking upward without ever leaving the tree.

One row is one folder, under crates/vleo-mod-<subsystem>/nodes/<row>/:

node.toml — the sheet. The only file written by hand — by a form's intake, or a developer. fixtures.toml — known-good values from outside this code. model.rs — generated, except the numbered slots where the Rust goes. contract.rs, mod.rs, evidence.rs, page.html, meta.json — generated.

The rules that do not bend, and the developer's loop, are in AGENTS.md; the reasoning behind the architecture is in docs/ARCHITECTURE.md.
