The method · how this page and every page in the tool teaches

The Feynman loop is the spine. Thirteen techniques hang on it.

You understand something by trying to explain it in plain words. Where you stall is what you do not know yet. The tool builds every explanation it gives, on a node page, a form, a result or a document, around that loop. This tab says how.

Answer first. The learner loop has ten moves: map, explain, find gaps, predict, source, ask why, create, simplify, iterate, teach. Thirteen techniques from the learning-science literature make each move work better. Six help you see the idea, three help you find your way, and four help you learn it. The tool already enforces fifteen rules (E1–E15, docs/EXPLAINING.md) built from these. Node pages carry only some of them so far. The Node pages tab lists the gap, and the Plan closes it.

What it is, and what it is not

It is explaining, not reading. Reading a clear explanation feels like understanding. People overrate how well they understand how things work until they try to explain them step by step. This is the illusion of explanatory depth Rozenblit & Keil 2002 [M5]. Feynman never published a four-step "technique". That name is a later popularisation Parrish [M4], built on habits he described: a name is not knowledge [M1], a notebook of things he did not know [M2], guess-compute-compare [M8], a "why" needs a floor [M9], and "what I cannot create, I do not understand" [M3].

Station 01 · purpose

Why the tool exists

Answer first. A spacecraft design is thousands of numbers that depend on each other. When they live in spreadsheets and scripts, copies drift apart, and nobody can say which number is current, where it came from, or what would break if it changed. This tool gives every number one home, one owner, one source and one release, and it shows its working.
  • 1,396 rows, one question each crates/vleo-mod-*/nodes
  • It was ported from a MATLAB study, row by row docs/MATLAB_PORT_PLAN.md
  • Every face shows the same engine's numbers AGENTS.md

1Say it simply

Imagine a team writing one big recipe book, where every page uses numbers from other pages. If everyone keeps a private copy, the books drift apart. One cook changes the oven temperature and the cake page never hears about it. This tool is the single shared book. Each page answers one question. Each page lists which pages it reads. Nobody can change a page by scribbling on their own copy. A change goes through the editor, who checks every page that reads it, and then everyone gets the new edition together.

ConcreteThe drag on the satellite depends on air density, which depends on the Sun's activity, which comes from forty years of solar records.
Picturesolar record → Ap, F10.7 → density → drag → propellant → mass → cost: one chain of rows, each reading the one before.
Equationanswerrow = frow(answers of the rows it reads). One function per row, and the resolver evaluates the graph.

2Now the real thing

The tree is a directed graph of 1,396 rows in four layers. A row is a sheet (node.toml), a generated contract and model, its fixtures, and a generated page. The kernel holds every formula. The resolver walks the graph for a case, a set of inputs. Every run prints "n ran, m blocked" and names the blocked rows. Results are saved under ~/.vleo/, keyed by the question asked, so the same question is not asked twice. AGENTS.md · README.md

3Where the simple version breaks

A recipe book has no physics. Here a page can be empty: of the 1,396 rows, 1,076 are still empty and 313 are published state = … in every node.toml. An empty row does not answer. It refuses by name, and so does every row that needs it. The tool tells you exactly how much of the design it can answer today, rather than looking complete.

Station 02 · structure

The tree: rows and four layers

Answer first. Rows sit in four layers. Management asks for what the mission needs (layer 1). The system decides what the satellite is made of and what reads what (layer 2). Subsystems do the physics (layer 3). The run is the case being evaluated (layer 4). A layer never reaches into the one below it. It reads a closure.
  • Layer 1: 174 rows · layer 2: 321 · layer 3: 901 layer = … in node.toml
  • Kinds: 663 declared, 306 computed, 214 required, 201 achieved, 12 KPI kind = …
  • 20 subsystem crates, one per layer-3 subsystem plus management and system crates/vleo-mod-*
It reads a closure. If management reached into a subsystem's formula, renaming or re-modelling that subsystem would silently change a cost. Through a closure, the contract is one requirement, one achieved value and one margin, and that contract is all that crosses the layer boundary.

1Say it simply

It is a company org chart for numbers. The board asks for results. Middle management turns them into targets for each department. Departments do the work and report back one number each: did we hit the target, and by how much? The board never walks onto the shop floor to read a machine's dial.

2Zoom levels

Four fixed zoom levels, never everything in one drawing (technique 6, the C4 model [M18]). Click a level.

3Now the real thing

Each row's sheet names its layer, its kind (declared is a value a person sets, computed is a relation, and required/achieved form a closure pair, as does kpi), its [[input]] rows, its [output] with a unit, bounds and the reason for each bound, and its [view]. The layer files in layers/ say which rows a layer contains and who owns them. CODEOWNERS is generated from them. docs/NODE_AUTHORING.md · layers/

Common wrong idea: "a row is a function."

A row is a question. Many rows are declared values with no formula at all (663 of them). A computed row's formula is not in the row either. It lives in vleo-core::physics, and the row's hole calls it (rule 3).

Where it breaks. Layers are a convention the graph enforces only at closures. The gate checks a closure's sense (7d, 7e), but whether a row is in the right layer is a review judgement. AGENTS.md "Requirements and closure"

Station 03 · the contract

Closures, and which way a requirement binds

Answer first. Between two layers, only a closure crosses: a requirement, an achieved value and a margin. Every requirement declares its sense. <= means the achieved value must stay under the bound, and >= means it must reach it. The sense is never defaulted, because the same number read the wrong way gives a comfortable margin for a spacecraft that is about to fail.
Case A · "the design sustains Ap 200"The sky the design can survive. Closes when the achieved storm level stays under 200.sense = "<="
Case B · "the design needs Ap 200"Something the design must reach. Closes when the achieved value is at least 200.sense = ">="
One difference: the direction. Same number, same unit, opposite verdicts. AGENTS.md

Try it · a closure, both ways

The achieved value 158.4 is the record's five-year return level of daily Ap, quoted in sw_ap_design's sheet crates/vleo-mod-solar/nodes/sw_ap_design/node.toml. The requirement of 200 is illustrative.

1Now the real thing

A requirement is any row of kind = "required", or any row that some closure reads as its req binding. The second part comes from the graph, not from a naming convention, because a folder rename can dodge a convention but cannot dodge a contract edge. Gate check 7d refuses a requirement with no sense. Check 7e refuses a closure whose hole applies Sense::AtLeast when the sheet says <=, or the other way round. AGENTS.md · crates/vleo-sheet/src/gate.rs

Why must the sense be declared rather than defaulted?
Because "sustains" and "needs" are written with the same number.
Why does that matter? A margin computed the wrong way still has a plausible sign.
Floor: a contract must state its direction, or it is not a contract. The prior MATLAB study failed its build without one for the same reason. AGENTS.md
Common wrong idea: "a positive margin is safe."

A margin is only meaningful with its sense. Not every closure runs the same way. A subsystem is promised to reach a target (≥), but the environment is not promised: nobody builds the Sun, so a solar requirement is the worst sky the design can sustain (≤).

Station 04 · the source

The sheet is the only source

Answer first. A person writes node.toml. The generators write everything else in the row's folder: contract.rs, model.rs except its numbered HOLE blocks, mod.rs, evidence.rs, meta.json and page.html. A hand edit anywhere else is overwritten by the next xtask docs, and the gate's regeneration diff fails it. A number and its reason are written once, by a person. Everything that repeats them is printed from that.

1Say it simply

The sheet is the master drawing. Shop drawings, labels and the parts list are traced from it by machine, so they can never disagree with it. If you scribble on a shop drawing, the next tracing wipes the scribble, and the inspector notices the drawing no longer matches.

Station 05 · the engine

Four rings, depending inward only

Answer first. vleo-units → vleo-core → vleo-bus → the subsystem crates → the faces. Each ring depends only on rings inside it. The kernel (vleo-core) holds every formula. It is no_std: no I/O, no clock, no drawing, and only portable maths, so the browser, Python and C all get the same bits.
  • Ring 0 units: types, frames, constants, pmath
  • Ring 1 core: physics, faults, the resolver
  • Ring 2 bus: the case, results and manifest every face posts
  • Ring 3: 20 vleo-mod-* crates behind the vleo-modules facade
ConcreteA Python analyst and a browser user ask for the same drag. They must get the same last digit.
PictureThe same kernel, compiled once for each face. No face carries its own copy of a formula.
Equationno_std + pmath ⇒ no platform maths library ⇒ identical results everywhere (rule 4).

Try it · a refusal is never a substitution

A toy graph of six rows. Untick a row to make it empty and watch its readers refuse by name. The tool's runs print the same "n ran, m blocked" line (rule 5). toy graph AGENTS.md rule 5

Why can't the kernel use f64::cos?
Because the kernel crates are no_std, where it does not exist. The compiler refuses.
Why choose no_std? So no clock, file or platform library can leak into a formula.
Floor: the same input must give the same output on every face, or two people looking at "the" answer are looking at different answers. AGENTS.md rules 3–4
Analogy · an onion

Each layer only touches the layer inside it. Peel the outer layer (a face) and the inside is unchanged.

dependency points inwardouter layers are replaceablean onion has no contracts between layersrings here are separate crates the compiler checks

Where it breaks. The facade vleo-modules and the server are larger than the rings suggest. They hold record keeping, figures and sweeps (phase 10 moved the solar statistics there). Those files are among the largest in the tree, and splitting them is planned (phase 13).

Station 06 · evidence

One external oracle

Answer first. Everything else in the system compares the software with itself. Fixtures are the exception: expected values from outside this code. The gate refuses a fixture whose provenance is self-snapshot or agent-generated (rule 2). A fixture disagreement is a physics disagreement. It goes to the row's owner, and the tolerance is never what changes.

Where the evidence stands

Of the 190 specified rows that compute, the best evidence each one has. Measured by the session banner on 1 Oct 2026. cargo run -p xtask -- status

Common wrong idea: "916 tests pass, so the numbers are right."

Most tests check that the code does what the code says. Only a fixture from outside can say the code says the right thing. Today 124 of 190 computing rows have no fixture at all, and 137 say nothing about where their relation comes from. Closing that is part of the plan (phase 16).

1Test the test

"A test that passes against a deliberately broken implementation is not testing anything." The gate's own checks are tested by breaking a copy of the tree and watching each check go red (gate evidence, docs_lint --selftest, panel_check --selftest). AGENTS.md "Testing"

Station 07 · faces

One engine, several faces

Answer first. The browser (served by vleo-server on 127.0.0.1), the command line, the Python wheel, the C ABI, the readers' folder (the kernel compiled to WebAssembly) and the form's own checker all reach the same engine. A face depends on the bus, never on a module, so adding a face cannot change a result. The browser talks to the engine only through 39 /v1 routes, each written down in contract/ with a schema and a recorded example.

Try it · pick a face, follow it to the engine

1Now the real thing

The contract test (the_contract_holds) refuses a field the engine sends that the schema does not declare, and a route the manual documents but the contract does not. A mock engine (tools/mock_engine.py) serves the recorded examples, so the page is proven to work with no Rust running. Within /v1 a change may only add. contract/README.md · docs/CHANGING.md §2

Through the busThe CLI posts a case on the bus. It cannot reach a formula, so it cannot change a result.
Into a moduleA face that called a module directly could pass it different defaults and get a "different" answer.

Station 08 · pictures

The engine computes, the page only draws

Answer first. A figure is data: a figure::Kind (line, scatter, bar, heatmap, animation, scene3d) with its series, axes and words, described by the engine. The page's player draws it. Since phase 10, no solar panel computes a statistic of its own. vleo figure <id> and Python's vleo.figure show the same numbers. 14 panels are declared in panels/, and a browser check proves each one renders, moves, reads what it declares and matches its approved picture.
Concrete"Days above the G-level bound in how many runs": a count someone could argue with.
Pictureengine → figure description (JSON) → player → pixels. The argument happens over the engine's numbers.
Equationpixels = draw(describe(engine(case))). Only engine holds statistics.
Common wrong idea: "recording a reference picture approves it."

Recording only stores what the page drew. A person must look and confirm. Some panel pictures are still marked UNCONFIRMED in panels/REVIEW.md. That is a job for a person, not for code. docs/CHANGING.md §3

Where it breaks. The panel check takes about 23 minutes in CI. During phase 11, three PRs (#88–#90) were merged before it finished. It later passed on main, but the plan makes "wait for the panel check" an explicit rule for merges into main (phase 13).

Station 09 · change

Who changes what, and how a change gets in

Answer first. The team uses the tool. The developers maintain it. A team member never edits the repository and the browser cannot change a row. When the design is wrong, the person who knows fills in the row's form and sends it. A maintainer runs xtask take, which puts it on its own branch, checks it, applies it, tests it and commits it under the author's name. The author tries a preview build and approves it. Then it merges and ships. An assistant may help write code, but it never supplies a relation.

A squash merge into maintainer/developer. A merge commit from developer into main, so developer stays an ancestor and the next PR carries only new work. The tag goes on the release PR's merge commit. docs/roles/maintainer.html merge-commit rule, adopted for #85

Typed into one copyNobody else checked it, nobody implemented it, and the next release does not have it.
Sent as a formChecked against every row that reads it, applied, tested, previewed, approved, released to all.
One difference: whether the change passes through the loop. That is why the browser has no edit button.
Why can't an assistant supply a relation?
A relation is confirmed by a person who has read it against its source and will own it.
Why enforce that in code? A sentence in a guide is a hope. intake refuses a form whose relation an assistant filled, and relation stamping refuses a checkout whose git name is an assistant's.
Floor: accountability needs a person's name on the mathematics. AGENTS.md · crates/vleo-sheet/src/form/who.rs

Station 10 · sharing

How results and releases travel

Answer first. A team member's inputs and results live in ~/.vleo/, outside the repository. A result is saved under the question it answers, so asking again finds it rather than re-running. Results can be pinned or thinned, sent as a .vleo file, or opened as a CSV or a self-contained HTML report. A release is four files: three kits (Windows, macOS, Linux) and one Python wheel that runs on any laptop. The release workflow builds them from a commit that a merged pull request put on main.

The wheel

python -m pip install vleo-0.4.0-py3-none-any.whl, then python -m vleo. Installed and started on Windows, macOS and Linux before it is published.

The kit

Extract and double-click Start VLEO.exe (Windows) or run ./start.sh. The daemon finds its files beside the binary.

The readers' folder

Every row's page and lesson, readable from a file with no tool running. The kernel compiled to WebAssembly answers the try-it widgets.

1Now the real thing

xtask ship <v> cuts release/<v> from main. It stamps every node version still marked next, sets the workspace version, regenerates the narrative, runs the gate and tests, then commits and pushes. Merging its pull request is the decision. The v<v> tag starts the release workflow, which refuses anything not on main or not put there by a merged pull request, and the version in Cargo.toml must agree with the tag. 0.4.0 was published this way on 1 Oct 2026. .github/workflows/release.yml · docs/RELEASE_SETUP.md

Where it breaks. The kits are not signed or notarised yet. That needs a certificate a release engineer controls, and the workflow does not pretend to sign. Windows and macOS warn on first open. release.yml header

Station 11 · failure

When something breaks

Answer first. The tool is built to fail loudly and stay up. A row that cannot answer refuses by name. A bug in one request ends that request and is logged, and the tool keeps running. Every write of a case or result is whole or not at all. Every command that writes prints numbered steps, leaves a trace, takes --dry-run, and on a stop says why, what state the files are in, and how to retry.
Something went wrong with…AskIt answers
a commandxtask explain <cmd>what it reads, writes and checks, how to undo it, where its code is
the last writing runxtask tracethe run, step by step, from target/xtask-trace/
a rowxtask why <node>its history, and its gate now
what is blockedxtask active · gapwhat answers, what is blocked by which named row, what sheets promised and nothing covers
a library callthe error's kind()Io · Missing · Malformed · Refused · Invalid · Unverified · Setting, with the same sentence as before (phase 11c)
Common wrong idea: "flaky, just re-run it."

"Flake" is not a root cause. A failure that reproduces is real. A test is never skipped or quarantined to get green, and a tolerance is never loosened to make a fixture agree. AGENTS.md "Testing"

Station 12 · standards

Every change says which belief broke

Answer first. Every change to a decision appends a [[version]] to the row: what we believed, what we tested, what we now know, what changed, what it rests on, and what would break it. Risks are registered once on the management layer and moved only by versions. Everything that teaches follows docs/EXPLAINING.md: answer first, said simply, the real thing with its source, then where it breaks. Every claim is tagged sourced, derived, declared or illustrative.

1Say it simply

Engineering is a story of beliefs that turned out wrong. Writing down each belief, the test that broke it and what replaced it turns "we changed the number" into "here is why, and here is what would make us change it again".

2Now the real thing

322 [[version]] records and 320 [explain] blocks exist today node.toml sections. The gate refuses a malformed record (versions, V17, V18). The gap pass holds a row that has none. xtask derisk regenerates the narrative, and xtask release stamps every next version with the release that ships it. tools/docs_lint.py refuses a document without "Answer first" and a "Kind" line, a Rust file without a //! line, and a stale path. docs/DERISKING.md · docs/EXPLAINING.md · tools/docs_lint.py

Station 13 · teach it back

The freshman-lecture test

Answer first. If you can explain the whole tool in five sentences to someone new, without notes and without its jargon, you understand it. If you cannot, the sentence where you stall is your next gap.

A five-sentence version, to compare

  1. Every design number is one row: one question, written once by a person in a sheet, from which its code, page and tests are generated.
  2. Rows sit in four layers, and only closures cross between layers: a requirement, an achieved value and a margin, with a declared direction.
  3. One kernel holds every formula, with no I/O and portable maths, so every face shows the same number, and a row that cannot answer refuses by name.
  4. A change arrives as a form, is taken onto its own branch, checked, previewed, approved by its author, merged and shipped to everyone in one release.
  5. Every change records which belief broke, expected values come from outside the code, and everything that teaches puts the answer first and says where it breaks.

Node pages · the upgrade

Every row's page becomes a station you can work through

Today a row's page already puts the answer first, tags its claims, says where it breaks and shows its evidence. This tab specifies what each row's page becomes: the full Feynman loop and all thirteen techniques, live against the engine, generated from the sheet like everything else.

Answer first. A row page will be one station with the same fixed order as this document. It opens with a live answer, the row's parts and its place in the tree. Then it says it simply, steps from concrete to picture to equation, contrasts two cases, gives the real relation with its source, follows a why-chain to a law, names a common wrong idea and says where the row breaks. It has a live try-it you can climb from one point to a sweep to a map, a rebuild-it from the author's own cases, and a place to teach it back. New content comes from new optional sheet fields, filled through the form by a person. A row without them shows exactly what it shows today.

How it stays honest

  • Generated, not hand-made. Every new block is a named part in web/pages/row.html, filled by page.rs from the sheet. A test proves a row with no new fields renders byte for byte as today.
  • Live, but the same engine. The try-it calls the served engine, or in the readers' folder the kernel compiled to WebAssembly. The page never computes a number itself.
  • A person's words. Explanations carry by, like [explain] today. The form refuses an assistant's name for them, as it does for a relation.
  • Checked. New gate checks: a contrast names one difference, a why-chain ends at a floor, an analogy lists at least one relation it breaks, and a predict question has exactly one right choice and a reason.

Phase 15 · the node page comes alive

The engine inside every row page

  • 15a the live answer: inputs as controls, and the answer recomputed by the served engine or the kernel's WebAssembly. A refusal is shown by name, with the row that blocked it.
  • 15b the ladder of abstraction: one point, then a sweep over one input (a line figure), then a map over two (a heatmap), all through the existing figure player.
  • 15c small multiples across the row's scenarios, on one shared axis.
  • 15d rebuild-it from the author's [[case]] entries: worked, then faded, then solo, checked against the case's expected value within its tolerance.
  • 15e a browser check for row pages, like the panel check: a sample of rows renders, a control moves the answer, and a refusal is named.

The one command that must be green

cargo run -p xtask -- gate && cargo test

The visual layer is outside it: python3 tools/panel_check.py.

Run the tool

cargo run --release -p vleo-daemon
cargo run -p vleo-cli --bin vleo -- run <node>

A change to the design, in order

xtask form <node>                         the form, to send out
xtask take <form.html> --for <author>     its own branch: checked, applied, tested, pushed
xtask approve <file>                      the author's approval of that exact build
xtask publish <node>                      a filled row's code generated, with holes
xtask build-node <node>                   a row from its method, tested on its cases
xtask fill <node> --hole <n> --body -     one hole, with --by and --model
xtask gate && cargo test                  green before any push
xtask ship <version>                      the release branch, stamped and proved
