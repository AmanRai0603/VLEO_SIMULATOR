VLEO integrated design tool · how the code works

One question, one answer,
one place it comes from.

This codebase answers 1,401 design questions about a very-low-Earth-orbit spacecraft. Every answer can be run, checked and traced back to the person who wrote it. This page explains how the code is built to make that true, from the sheet a person writes to the release everyone installs.

sourced stated in a named file of this repository derived worked out here from sourced facts declared a decision this project made illustrative example numbers for a widget
In short. The code is one engine with several faces. Every number is answered by one row, and each row is one node file in design/. Its node engineer writes it in the application, and it holds the row's sheet and its method, its relation in pseudocode. The engine reads the design from its files when it opens and runs every method in its interpreter; no Rust is written per row. The engine's kernel holds every formula, with no files, no clock and no drawing, so the browser, the command line, Python and C all get the same answer. A row that cannot answer refuses by name instead of guessing. A change to the design arrives in a group's sealed release, passes the gate, and is released to everyone at once.

01 · purpose

The problem it solves

In short. A spacecraft design is thousands of numbers that read each other. Kept in spreadsheets and scripts, copies drift apart, and nobody can say which number is current, where it came from, or what changes if it does. This codebase gives every number one home, one owner, one source and one release, and it shows its working.

In plain words

Think of a dozen cooks writing one recipe book, where every page uses numbers from other pages. If everyone keeps a private copy, the copies drift. Someone changes the oven temperature, and the cake page never hears about it. This tool is the single shared book. Each page answers one question and lists the pages it reads. Nobody changes a page by scribbling on their own copy. A change goes through an editor, who checks every page that reads it, and then everyone gets the new edition together.

A real caseThe drag on the satellite depends on air density, which depends on the Sun's activity, which comes from decades of solar records.
As a chainsolar record → Ap, F10.7 → density → drag → propellant → mass → cost. Each link is a row that reads the one before.
As codeanswerrow = frow(answers of the rows it reads). There is one function per row, and the resolver evaluates the graph.

Where the answers exist today

Rows per subsystem, split into published (they answer) and empty (they refuse by name). each row's state in design/, 9 Oct 2026

Where this picture stops being true

A recipe book is complete on day one. This one is not. 1,081 of the 1,401 rows are still empty, 313 are published and 7 are deprecated. An empty row does not answer, and neither does any row that needs it. The tool tells you exactly how much of the design it can answer today, rather than looking complete.

03 · the crates

The map of the code

In short. The code is 17 crates in crates/ (13 in the Rust workspace, four built outside it: the Python wheel and three WebAssembly engines), plus the xtask program. They sit in rings that depend inward only: vleo-units → vleo-core → vleo-bus → vleo-modules, the engine → the faces. The design is not in crates/: it is design/, its files, and nothing in the repository writes it. Two crates sit beside the rings: vleo-sheet (everything about sheets, never linked into a run) and vleo-data (reference data). xtask is the tool that generates, checks and releases.
  • Ring 0 depends on nothing. Ring 1 holds every formula.
  • Ring 3 reads the design from its files and runs it, with no formula and no design of its own.
  • A face depends on the bus and the engine, and reaches a row only through vleo-modules.
  • xtask graph checks that every dependency points inward, and CI runs it on every pull request.
Through the engine. If a face ran a row's method itself, it could run it with its own defaults and show an answer no other face shows. With one door, vleo-modules, every face gives the same answer, and adding a face cannot change a result.

Explore the crates

Click a crate. Its dependencies light up violet and its dependents amber, the same colours the tool's own tree view uses. The panel lists every source file, its length, and the line the file opens with. every Cargo.toml and every src/*.rs, 1 Oct 2026

Why must dependencies point inward?
So an outer piece can be replaced or added without changing an inner one. A new face cannot alter a formula.
Why does that matter here? Two people looking at "the" drag must be looking at the same number, however they asked for it.
One kernel, one answer: a formula exists in exactly one place, vleo-core::physics. AGENTS.md rule 1
Like an onion?

Each layer touches only the one inside it, and peeling an outer layer leaves the inside unchanged.

dependency points inwardouter layers can be swappedan onion has no contracts between layershere the compiler refuses a wrong edge
Where this picture stops being true

The engine and the server are bigger than "thin outer rings" suggests. vleo-modules also works out the statistics the solar figures draw (record.rs, 2,149 lines), and the server holds saved results (results.rs, 1,969 lines). They hold no formula of their own, but they are where most of the non-physics logic lives.

04 · a row's file

One row, opened

In short. Every row is one node file in design/, and nothing in the repository writes it. It holds the row's block, its ports and the wires into them, its test cases, and its texts: the method, the explanations, and the sheet it was converted from. The method is the row's relation in pseudocode, which calls formulas in the kernel by name. Someone outside the code supplies the test cases, the expected answers. A row a prior implementation already answered may carry that implementation's grid as a table. There is no Rust in the file: the engine runs the method in its interpreter, and the row's page is rendered from the sheet when it is opened.

Open sw_ap_design, part by part

A real row from the solar subsystem: "What daily Ap is this design built to survive?" The excerpts are from its node file, shortened with "…". design/groups/l3_solar/nodes/sw_ap_design.vnode

The doorThe resolver moves every value in SI as a plain number, through the one NodeTable in vleo-modules.
The methodInside, the interpreter works in declared types and units, and the method checker refuses a line whose units do not agree before it ever runs.
The one difference is whether values carry their unit. The resolver only moves numbers; a method only does arithmetic on quantities. So a unit mistake is refused by the checker, by name, instead of producing a wrong answer. vleo-modules/src/opened.rs · docs/PSEUDOCODE.md
A common misreading: "I'll fix the typo in the row's sheet here."

The sheet is its node engineer's. The fix goes back to its group and arrives in the group's next sealed release; nothing in this repository writes a node. A fault in the page's layout, not its words, is fixed in web/pages/row.html, the parts file every row page is printed from.

05 · generation

From sheet to code

In short. No code or file is generated for a row any more. The design as its files, design/, is what the engine reads when a face opens it; nothing here writes it, and a test refuses a sheet that comes back beside it. xtask docs writes one file, docs/PSEUDOCODE.md, the method language's reference. xtask assemble checks that the tree assembles and writes the index and the document. The gate regenerates everything and fails if any committed file differs. A number and its reason are written once, by a person. Everything that repeats them is printed from that.

Why does each row carry a sheet hash?
So everything that names a version of the design can tell one version of a row from another. The sheet hash and the method are in the design's files, and the engine reads both when it opens.
What happens when it changes? The graph's hash and the design's fingerprint change with it, so two computers that disagree about a row cannot claim to run the same design, and a saved answer from before is not passed off as today's.
A stale answer shown as current is worse than no answer. vleo-modules/src/lib.rs: graph_hash · design_fingerprint
Where this picture stops being true

The method language is small and fixed on purpose: named values with units, conditions, loops with a fixed limit, a refusal, and kernel functions called by name. A relation it cannot yet express is not written around in Rust. Its row stays open and is refused by its own name until the language grows, by a reviewed change to the kernel or the interpreter. The method is checked like code: the checker refuses a line whose units disagree, the interpreter has only pmath, and the node's declaration says who wrote or transcribed it.

06 · the engine at work

Inside a run

In short. A run takes a case and returns an answer for every row it reaches. The resolver computes the order from the graph; nobody writes it down. It hands each row its inputs as plain SI numbers, and the row is answered by its behaviour: a method run by the interpreter, a stated value, a lookup table, or its children. It keeps every answer in a fixed store, and reuses a row's answer only when nothing it depends on has changed. A row that faults stops its readers, and the run prints "n ran, m blocked" with every blocked row named.

Watch one run, from a click to a number

Press play, or step through. Each step names the files that do the work. resolver.rs · value.rs · credibility.rs · vleo-server three example rows

A refusal is never a substitution

A toy graph of six rows. Untick a row to make it empty, and watch every row that reads it refuse by name. toy graph AGENTS.md rule 3

Reuse keyed on the caseSame inputs give the same answer, so cache by the inputs.But rewrite a row's arithmetic without changing its interface, and the cache hands back yesterday's number as if it were current.
Reuse keyed on the chain hashEvery row the run reached, each one's implementation content and outputs, and the case.Change a row's method and every answer downstream is recomputed.
The one difference is whether the code itself is part of the key. Leaving it out is exactly the defect this system exists to prevent. vleo-core/src/resolver.rs
Why can't the kernel call f64::cos?
Because the kernel crates are no_std, where it does not exist. The compiler refuses.
Why no_std? So no file, clock or platform maths library can leak into a formula. The same kernel runs in the browser as WebAssembly, on a laptop, and on a target with no allocator.
The same inputs give the same bits on every face, using vleo_units::pmath, the one implementation of every transcendental function. AGENTS.md rule 2 · vleo-units/src/pmath.rs
Where this picture stops being true

A run is not always a straight line. Some subsystems close a loop: thrust needs available power, and power needs the thrust demand. A loop is declared as data in the case and iterated by the resolver. No row ever calls another, which is why such a loop never forces two subsystems into one row.

07 · the contract between layers

Closures, and which way a requirement binds

In short. Between two layers, only a closure crosses: a requirement, an achieved value and the margin between them. Every requirement declares its sense. With <= the achieved value must stay under the bound; with >= it must reach it. The sense is never defaulted, because the same number read the wrong way gives a comfortable margin to a spacecraft that is about to fail.
"The design sustains Ap 200"The worst sky the design can survive. It closes when the achieved storm level stays under 200.sense = "<="
"The design needs Ap 200"Something the design must reach. It closes when the achieved value is at least 200.sense = ">="
The one difference is the direction: same number, same unit, opposite verdicts. AGENTS.md

A closure, read both ways

The achieved value 158.4 is the record's five-year return level of daily Ap, from sw_ap_design's sheet sw_ap_design.vnode. The requirement of 200 is illustrative.

How it actually works

A requirement is any row of kind = "required", or any row a closure reads as its req binding. The second part comes from the graph, not from a naming convention, because a folder rename can dodge a convention but not a contract edge. Gate check 7d refuses a requirement with no sense. Check 7e refuses a closure whose method says margin_at_least when its requirement says <=, or the other way round, because two statements of one fact drift. AGENTS.md · crates/vleo-sheet/src/gate.rs

A common misreading: "a positive margin is safe."

A margin means nothing without its sense. Most closures are a promise: a subsystem must reach what it was asked for (≥). The environment is not promised, because nobody builds the Sun. So a solar requirement is the worst sky the design can sustain, and it closes when the achieved sky stays under it (≤).

08 · data

Reference data: never fetched during a run

In short. Solar records, coefficients and validated cases arrive as named, versioned, immutable bundles, each with a manifest and a content hash, plus a lockfile of what is installed. One explicit sync puts them on disk. A run either has verified data on disk or refuses to start. It never fetches, waits, retries or silently falls back. A campaign of a million cases makes zero network calls. crates/vleo-data/src/lib.rs

Where this picture stops being true

Bundles are CSV for now, so anyone can read them in a text editor. The intended format is columnar (Parquet, read in process). It is not built yet, deliberately: it waits for the first bundle that does not fit comfortably in memory as text.

09 · faces

One engine, several faces

In short. All of these reach the same engine through the bus and vleo-modules:
  • the browser, served by vleo-server on 127.0.0.1, so the page and the engine share one origin with no internet needed;
  • the command line;
  • the Python wheel;
  • the C ABI;
  • the readers' folder, which runs the kernel as WebAssembly;
  • the method checker the group and node pages carry, also WebAssembly.
The browser talks to the engine only through the routes written down in contract/, each with a schema and a recorded example.

Pick a face and follow it to the engine

The routes the browser can call

Every route in contract/routes.toml. Type to filter. A route the manual lists but the contract does not, or a field the engine sends but the schema does not declare, fails the_contract_holds. Within /v1, a change may only add. contract/routes.toml · contract/README.md

How it actually works

A mock engine (tools/mock_engine.py) serves the recorded examples, so a check proves the page works with no Rust running. The Python wheel starts the same vleo-server inside python.exe, so the browser and Python cannot disagree. The C header is generated from the same declarations as every other binding.

10 · the web face

The browser: modules that only draw

In short. The page is plain ES modules in web/js/, styled by web/app.css and set in the bundled IBM Plex Mono. It has no framework and no build step. Every page the tool writes as a file is web/page.html with its slots filled, from named parts in web/pages/. The page computes nothing: it asks the engine and draws the answer.

The modules

Click one to see what it is for. the opening comment of each web/js/*.js

How it actually works

app.js boots the page, routes and attaches every event listener. state.js holds the one state and the graphs derived from it. Views read that state: the tree, paths and matrix columns, a node, the results, the manual. run.js calls /v1/run and /v1/sweep. figures.js plays any figure the engine describes. depth.js switches the Learn · Read · Expert depth on every page that has it.

A common misreading: "the chart works out the percentile."

Since release 0.4.0, no panel computes a statistic of its own. The engine works out every number a figure draws (vleo-modules/src/record.rs), and the page only draws it. vleo figure <id> and Python's vleo.figure return the same numbers.

13 · change

How a change lands

In short. Everyone uses the tool; the developer maintains it. Nobody who uses it edits the repository, and the browser cannot change a row. A node changes in its own file, written by its node engineer, and the subsystem engineer seals the group's work as a release and puts it on the shared drive. When the tool opens on the drive, it builds today's design from every group's latest sealed release that passes its checks — its seal, its content, each node against the design — and says which release each group's part is, and why one was refused. Nobody takes a release in by hand. The developer releases the tool. An assistant may help write code, but it never supplies a relation.

Walk one group's release from its node files to today's design

The branches

Feature branches are squash-merged into developer, and a pull request takes developer into main. A group's sealed release comes through no branch: it goes on the shared drive. developer goes in with a merge commit, so the next pull request carries only new work. A release is cut from main. CONTRIBUTING.md · docs/GROUP_APPS.md

Typed into one copyNobody else checked it, nobody implemented it, and the next release does not have it.
Sealed in a group's releaseSigned by who wrote it, sealed, put on the shared drive, checked against the design, then in today's design for everyone.
The one difference is whether the change passes through the loop. That is why the browser has no edit button.
Why can't an assistant supply a relation?
A relation is confirmed by a person who has read it against its source and will own it.
Why enforce that in code and not just in a guide? A sentence in a guide is a hope. Today's design refuses a release whose method or results an assistant supplied, and a release's checks refuse a signature in an assistant's name.
Accountability needs a person's name on the mathematics. crates/vleo-sheet/src/form/who.rs

14 · releases and results

How releases and results travel

In short. Each person's inputs and results live in ~/.vleo/, outside the repository. A result is saved under the question it answers, so asking again finds it rather than re-running. Results can be pinned, thinned, sent as a .vleo file, or opened as CSV or a self-contained HTML report. A release is four files, built by CI from a commit that a merged pull request put on main: three kits and one Python wheel for any laptop.

The wheel

python -m pip install vleo-0.4.0-py3-none-any.whl, then python -m vleo. Installed and started on Windows, macOS and Linux before it is published.

The kit

Extract it, then double-click Start VLEO.exe on Windows or run ./start.sh elsewhere. The daemon finds its files beside the binary.

The readers' folder

Every row's page and lesson, readable from a shared drive with no tool running. The kernel, compiled to WebAssembly, answers the try-it widgets.

How it actually works

  1. xtask ship <v> on main cuts release/<v>. It regenerates the de-risking narrative, sets the workspace version, regenerates, runs the gate and the tests, then commits and pushes. It stamps nothing in the design: a row's versions are its node engineer's.
  2. Merging its pull request is the decision to release.
  3. The v<v> tag on that merge commit starts release.yml. It refuses anything not on main or not put there by a merged pull request, checks the tag against Cargo.toml, builds the four files, smoke-tests the wheel, and publishes.
Where this picture stops being true

The kits are not signed or notarised. That needs a certificate a release engineer holds, and the workflow does not pretend to sign. Windows and macOS warn on first open. .github/workflows/release.yml

15 · failure

When something breaks

In short. The code fails loudly and stays up:
  • a row that cannot answer refuses by name;
  • a bug in one request ends that request, is logged to a crash file a person can send, and the tool keeps running;
  • every write of a case or result is whole or not at all.
Every command that writes prints numbered steps, leaves a trace, takes --dry-run, and when it stops says why, what state the files are in, and how to retry.

A common misreading: "it's flaky, just re-run it."

"Flaky" is not a root cause. A failure that reproduces is real. A test is never skipped to get green, and a tolerance is never loosened to make a fixture agree. AGENTS.md "Testing"

17 · check yourself

Explain it back

In short. If you can explain the whole codebase in five sentences to someone new, without notes, you understand it. The sentence where you stall is the chapter to read again.

One five-sentence version

  1. Every design number is one row, written once by a person in a sheet whose method states its relation, and the engine reads the design from its files and runs every method in its interpreter.
  2. Rows sit in four layers. Only closures cross between layers: a requirement, an achieved value and a margin, each with a declared direction.
  3. One no_std kernel holds every formula, the resolver runs the graph, and every face reaches it through the same bus. A row that cannot answer refuses by name.
  4. A change arrives in a group's sealed release on the shared drive, and the tool builds today's design from every group's latest release that passes its checks, for everyone who opens it.
  5. Expected values come from outside the code. Reference data is synced before a run, never fetched during one. Every command says what it did and how to undo it.
