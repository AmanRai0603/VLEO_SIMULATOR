# F8 · Bringing data in

> **Answer first.** Whatever an engineer already has, the application takes as it is: a formula typed as written, a number with its unit, a range or a spread, a pasted table, CSV results, a flight-software harness's measurements, a PDF, or a similar node to start from.
>
> **Kind:** brief · **For:** Person A, S3 (start) and S5 (finish)

Plan: `docs/PLAN_F.md`, F8 and decision 10. The operating model: section 7,
every row of its table; section 8, point 3.

## Builds

**S3 · typed formulas and units.**
- A formula typed as written (`D = 0.5 * rho * v^2 * Cd * A`) made a method:
  its inputs found, their units asked, the method checked as any other.
- Units as people write them (`250 km`, `55 mN/kW`), through the engine's own
  unit parser; a range or a spread as typed (`2.5e-11 to 1.5e-10`,
  `55 ± 10%`).

**S5 · tables, results and flight software.**
- A table pasted from any spreadsheet, as copied: a lookup, or cases.
- CSV results from MATLAB, Python or a spreadsheet: cases, marked with their
  source.
- A flight-software harness's results file: its outputs as cases against the
  method, and its time, cycles, stack and memory as values the design's
  budgets close on (decision 10).
- A PDF dropped beside a node as its source; *start from a similar node*.

Each way in shows an example beside it and its error in plain words as it is
typed, and writes into the node through the library like any other edit.

## Proved by

One scenario for each way in, each ending in a node whose cases agree.

## Not in F8

An `.xlsx` reader (decision 8). Building or running embedded code
(decision 10).

## F8-a · typed formulas and units, S3's half (planned 18 October)

Planned from the code at 3ed29817, A's line with F1 to F6-c's c1 and c3a in
it. **Two of its four pull requests are high risk:** one changes how the
engine reads a unit (rules 3 and 5); the other is a new way a method gets
written (rule 6). Opus reviews each; Aman approves. Nothing here computes a
relation: a typed formula becomes the node's method text, `compile` checks
it against the node's ports, and the interpreter judges it on the node's
cases. Every unit is read by the method language's own `parse_unit`.

### What it starts from, found while planning

- **The method language is `vleo_sheet::method`**, one implementation read
  by the gate, intake, the library's checks and the engine
  (`vleo-sheet/src/method.rs`): `parse::parse`, `check::check` and
  `compile` against a `Signature` (the inputs' names and dimensions, and the
  answer's), `run::Compiled`. The engine reaches it through
  `node::node_program` from `opened::interpreted`; the library through
  `method::report` (`checks.rs`).
- **What the language takes:** `+ - * / ^` (no `**`: read as two `*` and
  refused); `^` binds tighter than a unary minus, to the right; 31
  functions, the kernel functions, and 21 kernel constants by name (`PI`);
  a literal's unit in brackets after it, `6371 [km]`; statements `let`,
  `const`, `set`, `if`, `for`, `while … at most N times`, `refuse`,
  `return`, `publish`. There is no bare assignment: `D = 0.5 * rho * v^2 *
  Cd * A` typed into *its method* is refused on line 1. Names are ASCII, and
  a non-ASCII character is reported as a stray byte («Ï» for `ρ`).
- **A method reads its inputs by the port's name.** The schema's port
  `symbol` ("the symbol its method writes it as") is read by nothing, and the
  fill route does not take one.
- **Two text kinds hold a method, read by different code.** `pseudocode`, a
  release's shape, is what `edit::Edit::Method` writes and what the checks,
  the breakdown, the page and format-1 intake read. `method`, `design/`'s
  shape, is what `convert::node_back` reads, and so what the engine runs. A
  node brought up to 1.0's checks holds both; nothing keeps the two bodies
  the same. Which shape is the one is F3-g0 (F3, question 9).
- **The unit parser is `vleo_sheet::method::parse_unit`** (`units.rs`): a
  `Unit` symbol whole, or symbols joined by `*`, `.` and `/` with a
  whole-number `^`. It reads `km`, `mN/kW` and `1/m^3`; it refuses `kg/m3`,
  `°C` and `µN` by name. `Unit` has 59 variants: kelvin only, no byte, no
  cycle. Nothing reads a number with its unit (`250 km`) today.
- **The engine reads units in a second spelling, and falls back silently.**
  `design/`'s 353 ports with a unit hold `Unit` machine names (`Kilogram`);
  a release's hold the language's symbols (`kg`). The engine reads both with
  `Unit::from_name(name).unwrap_or(Unit::One)` (`opened.rs`, and
  `page.rs`): a symbol, or anything unknown, becomes a pure number with
  factor 1. A range framed in `km` reaches today's design read as metres; a
  ratio stated in `%` is read as 55, not 0.55. **This is a substitution
  (rule 3), and F8 would widen it.**
- **Ranges** are `port.lower`, `port.upper` and `port.range_reason`, text,
  in the port's unit. An input's default must lie inside its range; an
  allocation is a value or both ends. Filling a port again drops its value
  and reason. An end that is not a number passes the frame and is refused
  only on conversion. An allocation's unit is never compared with the
  output it bounds.
- **Who writes what.** A node engineer writes the method, cases and
  explanation through `vleo_files::edit` (`POST /v1/node/<id>/edit`, with a
  dry run; the Node workspace's *write it*). Ports and wires are not edited
  there; they are asked for (kind `contract`). The branch's owner frames
  ports (`breakdown::Edit::Fill`, `frame::allocate`), with no dry run.
- **The declaration** (`declaration.csv`: author, `ai`, date, source,
  checked by) is restated with every method edit; `relation` is refused,
  `transcribed` counts only with a source and a checker, and an empty `ai`
  is refused. The page never fills in `ai`.
- **Nothing turns a formula into a method, or finds its inputs.**

### Builds

1. **The engine reads every unit with the one parser** (high risk).
   `opened::unit_of` and `to_si`, and `page.rs`'s readings, take a machine
   name or anything `parse_unit` reads; anything else refuses the row by
   name, never read as One. A unit `parse_unit` reads that has no `Unit`
   variant (`mN/kW`) is refused by name in the engine until `vleo-units`
   has one. `design/` holds machine names only, so no answer moves, and
   `baseline/today.csv` proves it.
2. **Amounts as typed:** `vleo_sheet::method::amount::read(text,
   field_unit)`, beside `parse_unit`. A value (`250 km`, `250 [km]`,
   `2.2`), a range (`2.5e-11 to 1.5e-10 kg/m^3`) or a spread (`55 ± 10% mN`,
   `55 +/- 5.5 mN`), the number read as the lexer reads one, the unit by
   `parse_unit` alone, and a spread's ends worked out as decimals from the
   digits typed (`49.5`, `60.5`). It holds what was typed, the nominal and
   the ends in the unit typed, the unit's factor to SI and its dimension in
   words. Refused by name, with the fix: an unknown unit or `°C`; a comma in
   a number; ends of different dimensions or backwards; a per-cent spread on
   a `%` field; a bare number in a field whose dimension is not pure;
   superscripts and `x10^`.
3. **A formula typed as written:** `vleo_sheet::method::formula::read(typed,
   signature, ports, units)`. One line `NAME = EXPR`, a bare expression, or
   several lines, the last the answer and each before it a `let`; each
   expression parsed by the method's own parser. `**`, `×`, `·` and `−` are
   written back as `^`, `*`, `*` and `-`, and the rewrite is shown; any
   other character is refused, named. Every name read that is not an
   earlier `let`, a constant or a function is an input, matched to a port by
   name, else by symbol (written as a `let` alias); one that matches neither
   is refused and listed as missing, a near name offered and never taken.
   Inputs come in as dimensioned values in their port's unit; for an
   empirical fit the person names each unit and the method reads each input
   as a number in it (`/ 1 [kW]`, `* 1 [kg]`). The program never chooses a
   unit. The method text starts `# Typed as: <the formula>`, and `compile`
   checks it. Nothing runs here.
4. **A typed formula goes through the library's edit** (high risk):
   `Edit::Formula { typed, units }` becomes `Edit::Method` with the text
   `formula::read` makes, held to everything a method edit is held to: the
   node's shape, the declaration restated and checked, the record of which
   belief broke, the save. The signature comes from the node file's ports
   through a `checks::node_signature` shared with `method_cases` and
   `child_ready`. The declaration is the person's, on the existing form.
5. **The route:** `POST /v1/node/<id>/edit` gains `formula` and
   `formula.units`; its answer, the method text, the inputs found with their
   units, and the diagnostics; in the contract. Missing inputs offer *Ask for
   these inputs*, the existing `/ask` route, kind `contract`, its body drafted
   from the names and units for the person to change.
6. **The Node workspace's *type a formula***, in *write it*, above *its
   method*, with its example beside it. The dry run shows each input found,
   the method it becomes, the diagnostics, and each case agreeing or not.
   *Use it as the method* puts the text into *its method*.
7. **Amounts in the System workspace's frame forms.** Fill takes `amount`,
   `symbol` and the two reasons and keeps the port's value; allocate takes
   `amount` and the reasons. The library reads each with `amount::read` and
   writes the unit typed. Refused by name: an end that is not a number, an
   allocation of another dimension than the output it bounds, a default
   outside its range. `GET /v1/amount?text=&unit=` reads one amount and
   writes nothing, in the contract.

### Not in F8-a

Pasted tables, CSV results, a worked example as a case, flight software, a
PDF, *start from a similar node* (S5). The System workspace's sheet (F5). A
formula with a condition, a loop, a list or several published values: those
are written as a method. A port added by a node engineer: they ask (F3,
question 10). New units or quantities (`mN/kW`, Celsius, bytes, cycles):
each a reviewed change to `vleo-units`, raised as a request (W14). The
equation drawn on the node's page. A spread read as a distribution.
Recognising a typed formula as a relation the kernel holds. The node shape
(F3-g0).

What S3 must not preclude for S5: `amount::read` takes one cell at a time,
so a pasted table or CSV reads each cell and header unit with it;
`formula` finds inputs against a signature, so a pasted lookup can become
`const` lists and `interp` through the same edit; unknown units are refused
by name, so flight-software measurements arrive as requests for
`vleo-units`, never as pure numbers.

### Risks

## F8-b · tables, results, flight software, a source and a similar node, S5's half (planned 23 October)

relation: a pasted lookup becomes method text that `compile` checks and the

### What it starts from, found while planning

- **F8-a is in four branches, none holding all of it.** a3 (the typed
  formula) is on a2; a4 (amounts in the frame) is a2 with a1 merged. F8-b's
  first pull request merges a4 into a3's line, so `amount::read`,
  `formula::read` and the engine's unit refusal are all under it.
- **Cases are one table in a release-shaped node:** `results/isolation.csv`,
  a column per input named as its port with its unit in the header
  (`lead [d]`), `answer [unit]` and `answer.<member> [unit]`, `tolerance`
  (relative), `refuses`, `origin` (`code`, `hand`, `spreadsheet`, `paper`)
  and an optional `says` (`groups/SPEC.toml`). There is no per-case source
  column: `origin` is the only mark. `edit::Edit::Cases` writes it from CSV
  text, refusing a row without an origin from that list; signing needs a
  header unit equal to the port's, three cases and a refusal, one row at
  every default, and every tolerance above 0.
- **The method language holds a 1-D table already:** `const NAME = [a, b, …]
  [unit]` and `interp(x, XS, YS)`, linear, clamped at both ends, x strictly
  rising. design/ writes 22 lookups this way. There is no 2-D table and no
  log read. A `lookup` behaviour exists in the schema and the engine, but no
  node uses it and `check_node` refuses it; `formula::read` refuses `[`.
- **CSV:** `vleo_files::csv` reads RFC 4180 with commas only. A tab-separated
  paste is read only by the old group page (`web/js/gtable.js`). The Node
  workspace has no paste and no file drop.
- **A source file has a place but no way in:** the `media` table (`scope,
  path, media_type, sha256, bytes`) is a node's own row, signed with the
  block and carried by issuing and intake, but no edit and no route writes
  one, and design/ holds none. `sources.csv` (id, cite, file, url, licence)
  is checked by `folder.rs`; `groups/SPEC.toml`'s limits allow a PDF of up
  to 5 MB and refuse `.xlsx` and `.docx`.
- **Nothing copies one node's content into another,** and a node engineer
  writes only the question, the explanation, the method, the cases and the
  formula. **An issued node is in neither shape, so every edit refuses it**
  until F3-g0 decides the one shape (F3, question 9).
- **The engine does not read `closure` rows,** and no unit holds what flight
  software measures: time has `s`, `min`, `h`, `d`, `yr` (no `ms`, `us`);
  data has `bit` and `GB` (no `B`, `kB`, `MB`); there is no cycle.
  design/'s `l3_fsw` budgets (throughput, memory, clock) are open nodes with
  no unit or value.

### Builds

1. **b1 · a pasted table or a CSV file as cases (high risk).**
   `vleo_files::table::read`: text pasted from a spreadsheet (tabs) or a CSV
   file (commas), its first row naming columns as the node's ports
   (`lead [d]`, `answer [sfu]`), each cell read by `amount::read` in its
   column's unit and converted to the port's, a refusal row marked as such.
   Written by `Edit::Cases` with an origin the person gives once for the
   paste, never defaulted. The Node workspace's cases gain *Paste a table*
   and *Drop a CSV*, read back as typed, with what each cell became, before
   the dry run judges every case.
2. **b2 · a pasted table as a lookup (high risk).** Two columns, x and y, each
   with its unit, become `const` lists and `return interp(x, XS, YS)` in the
   method, through the same edit as a typed formula: inputs found by name,
   the declaration restated (`none` with its source, or `transcribed`),
   checked as any method and judged on the node's cases. Refused by name: x
   not rising, fewer than two rows, a second x column, a log read.
3. **b3 · a source beside the node.** `Edit::Source`: a PDF, or the CSV file
   b1 read, as a `media` row under `sources/`, listed in `sources.csv` with
   its cite, signed with the node and put back with it. The node's page
   links it. Refused: another type, over 5 MB, a name that is not a plain
   file name.
4. **b4 · a flight-software harness's results.** Its file, CSV with a row a
   case, its inputs, its outputs, and `time`, `cycles`, `stack` and `memory`
   columns: the outputs become cases through b1 (origin `code`), the file
   is kept as a source through b3, and the measurements are shown, worst
   case first, beside the budget each would close on. Writing them into the
   design waits on two people: the developer, for the units (`ms`, `B`,
   cycles) as a reviewed change to `vleo-units`, raised as a request (W14)
   from the screen; and the branch's owner, for a port to hold each, asked
   for as a contract change (F3-d).
5. **b5 · start from a similar node.** In the Node workspace, a node of the
   design whose ports match by name and unit is offered; its question,
   explanation, method and cases are drafted into the edit form, never
   saved until the person saves them, with the declaration's source naming
   the node copied and the cases keeping their origins.
