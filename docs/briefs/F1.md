## Decides first (B's open questions)

1. **Who owns a group.** `chain::owner_of` reads the programme's mounts, but
   `design/` mounts the groups in the systems' file. Ownership follows the
   mount wherever it is: a group's subsystem engineer is the person assigned
   the block that mounts it, in the file that holds that mount. The chain
   becomes programme → systems → group: the systems' file opens through the
   programme's, signed by the registered system engineer or their deputy, and
   a group file opens through whichever file mounts it.
2. **`chain::open_group` admits only a subsystem engineer,** so the systems'
   file cannot open through it. The systems' file gets its own opener,
   `open_systems`, that admits the system engineer.
3. **Run my code again (PR 169)** is limited to the nodes assigned to the
   person whose key is open. Anyone else's is refused, saying whose code it is
   and why. Proposed here; Aman decides when he approves this PR.

## Builds

**PR 1 · keys and identity (high risk).**
- Library: `open_systems`; `owner_of` searching the file that mounts the
  group; `whoami(anchor, programme, systems, groups, public key)`, giving the
  person, their roles, the groups they own, the nodes assigned to them and
  whom they deputise for.
- Program: the private key lives as `<person>.vkey` on the person's computer
  (`~/.vleo/keys/`), never on the drive. `POST /v1/key/make`,
  `POST /v1/key/open` (the passphrase in the body, on loopback only, never
  logged), `POST /v1/key/close`, `GET /v1/me`. An opened key is held in
  memory only, and dropped on close or exit.
- The anchor: the programme manager's fingerprint from START HERE, shown on
  first use and remembered in `~/.vleo/anchor`; a later change of it is
  refused with the reason (section 14).

**PR 2 · People and the base version.**
- People: register, replace and revoke a key, at the valve that owns it (the
  programme manager in the programme's file; a subsystem engineer for their
  node engineers in their group file). Each is a write through the library,
  signed with the registrar's key.
- `base_version`: a whole number that rises by one with each released
  design, beside the `based_on` label that is already in every file's meta.
  The library reads and checks it; F2 shows it and F5's seal records it.
- The drive folder the copy came from, remembered beside the working copy in
  `copied.toml` with the SHA-256 of every file as it was copied, so F3 can put
  a person's own signed files back and never over one that changed on the
  drive since (decision 3).

**PR 3 · the shell and My work.**
- The application's shell: five workspaces named, four of them empty;
  choosing the database folder; making and opening a key; People.
- My work, with the first items the files can say: nodes assigned and
  unsigned, nodes failing, a group with nothing sealed.

**As built (PR 175).** My work says a node of yours unsigned or with no file,
a group of yours with nothing sealed, and a file below you the chain refuses.
Three things moved:
- *Nodes failing* waits for F3, which runs a node's checks for the person.
- *The programme manager anchors the empty drive* waits for a route that
  writes the programme's file and START HERE, and for F3-c's put-back to
  let anyone else see them. The check starts from a drive already anchored.
- *Registers the system engineer, who finds his role* is shown with a
  subsystem engineer. A system engineer registered now holds a systems'
  file signed before his key counted, which the chain rightly refuses until
  he signs it again (F5, F6).
