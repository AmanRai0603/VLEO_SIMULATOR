# F4 · The breakdown

> **Answer first.** The owner of a branch grows its breakdown in the application: a block added, broken down, moved, renamed, split, folded back or removed, each with its history saying why, and a node broken down only if its children reproduce its cases.
>
> **Kind:** brief · **For:** Person A, S3 (Friday 16 October, day)

Plan: `docs/PLAN_F.md`, F4. The operating model: W13; the system model:
`docs/SYSTEM_MODEL.md`, sections 2 and 3.

## Starts from

- The format-2 schema's `block`, `wire`, `mount`, `change` and `request`
  tables; `vleo_files::n2` (the N2 and the loops of a design).
- F3: a request for a breakdown, written in the node file.
- The old group page's structure editor (`web/js/gstruct.js`), format 1:
  reused for its interactions, not its file handling.

## Builds

1. **Each edit through the library,** with a `change` row saying who, when
   and why: add, break down, move, rename, split, fold back, remove.
2. **An open block filled a part at a time,** and every branch showing what is
   still open.
3. **Breaking down a node:** its behaviour becomes its children, its old
   relation kept as its estimate; its own cases run against the children,
   beside the estimate.
4. **The branch as a tree** in the System workspace, editable by its owner
   only.

## Proved by

- A node broken down whose children reproduce its cases, accepted.
- One whose children do not, refused by name, with the case that disagrees.
- An edit by someone who does not own the branch, refused.

## Not in F4

Mounting a new group on a node (F6, W13's second choice).

### What it starts from, found while planning

- **A branch's shape is its group file's.** The group file holds the
  headings, blocks whose behaviour is `children`, and every row has a node
  file of its own (`convert.rs`). A block is in exactly one file
  (`n2::Design::of`), and a node file's frame (`id`, `parent_uid`,
  `contract_version`) is not its writer's to change (`save`).
- **A group file stays in the copy.** People's changes are signed into the
  copy by whoever made them, and put-back takes no group file back (F3-c).
- **Today's design is built from sealed releases only,** so nothing framed in
  the copy shows there before F5 seals it.
- **Nothing checks that children reproduce their node's cases.** The engine
  runs a `children` row's cases against its estimate and leaves the
  integration check to the group. The library can make it with what it has:
  each child's method run by `vleo_sheet::method`, the node's own cases
  (`results/isolation.csv`, read as `checks::method` reads them) as the
  evidence, and their own tolerance. No formula outside the kernel; no
  expected value from the code under test.

### F4-a · each edit through the library (high risk; Opus review, Aman approves)

- **The group file only; no node file is written.** An edit writes the
  group file in the copy, re-signed by its editor, refused unless it still
  opens through the chain (as People's changes are).
  - **Add** a block (behaviour `open`) under a live block of the branch, and
    **fill** an open block a part at a time: its question, then each port.
  - **Break down** an issued node: one `wire` per output of the node into the
    group file, from the child's port that answers it. The node's own file is
    untouched, its method, cases and signature its estimate; its ports and
    contract do not change (SYSTEM_MODEL, section 2: its outside stays). F5
    re-issues its file as `children` and issues the children's.
  - **Move, rename, split** an open block, **fold back** a broken-down node
    (its answering wires removed; its children stay, in the history), and
    **remove** a block (archived, never deleted).
  - Each refused, with nothing written, by name: an id taken or not lower
    snake case; a cycle; a block that answers a broken-down node, is read by
    a wire, is assigned or has live children; a block that carries a mount
    (F6); an issued node moved, renamed, split or removed (F5's re-issue); a
    port's type or state the schema does not allow, a unit that does not
    parse, a range upside down.
- **Who may edit:** the branch's owner, read from the file that mounts it, or
  their deputy, with a key that counts now. One function for it,
  `chain::may_frame`, which People's changes use too; the screen asks it,
  never works it out. The programme's branch is refused (F7).
- **Each edit says why:** a `change` row, `what` = `<edit>: <why>`, with the
  rows it touched before and after. An empty why is refused.
- **Children reproduce the node's cases** (`breakdown::reproduces`): the
  children run in wire order on each of the node's cases, a child's input
  wired from where the node's own input comes taking the case's value. Each
  case agrees within its own tolerance, or is named with what the children
  gave and what it expects. A child that cannot run (open, a lookup, no
  method) is named and not run. Checked at the breakdown, which is refused
  unless every case agrees; shown at all times; F5's seal will require it.
- **Proved by** `crates/vleo-files/tests/a_branch_is_broken_down.rs`, on
  solar 1.1's `sw_activity_band` with two children placed as F5 would issue
  them: one carrying its transcribed method, accepted; one whose elevated edge
  is 135 sfu, refused naming the case at 130 sfu. Expected values are the
  release's own, as literals. Every refusal above; the change row and its
  why; a second writer; someone not owning the branch, and a deputy; node
  files' bytes unchanged. Each test shown red first.

### F4-b · the branch as a tree in the System workspace (medium risk; Opus review)

- `GET /v1/branch?group=<id>`: the branch's tree from your copy, said so;
  each block's behaviour, what is still open in it and below it, its
  answering children and whether they reproduce its cases, case by case
  beside its estimate; whether it is yours to edit (`chain::may_frame`), its
  signature, its history, and the next step.
- `POST /v1/branch/<edit>`: each edit, with `opened` (a second writer stopped)
  and `why`; carries the launch's word.
- `/app`'s System workspace: the tree on the left, coloured by behaviour and
  marked with what is open; the block chosen on the right, with its estimate
  beside its children per case, its history, and the edit forms only for its
  owner.
- **Proved by** a program test through the routes and `tools/branch_check.py`
  (Playwright, the panels job): Ola frames solar, adds and fills a block,
  breaks a node down into children that do not reproduce it (refused on
  screen, naming the case, nothing written) and into ones that do
  (accepted), and folds it back; Pia sees no edit offered, and her edit sent
  anyway is refused by name.
