   nothing is written, if the file changed in the folder since it was opened

### F3-a · a revision saved in place (medium risk)

- **Library: `folder::save(copy, path, file, opened)`.** `opened` is the
  SHA-256 of the file's bytes when the person opened it.
  - Before writing, the bytes on disk are read again. If they differ from
    `opened`, the save is refused as *a second writer stopped*. The refusal
    names the writer and the revision now there. Nothing is written.
  - Otherwise the file is checked before it is written (`check_meta`, and the
    node's own checks as the gate runs them). The revision rises by one.
    `writer` must be the person whose key is open and who is assigned the
    block. The file is written whole to a temporary file in the same folder,
    then renamed over the old one.
- **Program:**
  - `GET /v1/node/<id>/file` gives the node and its `opened` digest.
  - `POST /v1/node/<id>/save` takes the edit and `opened`. On a conflict it
    answers both versions, so the screen shows them and the person keeps one.
  - Saving needs an open key, but no signature.
- **Proved by:**
  - A library test: the bytes are changed between open and save, the save is
    refused, and the file is the same, byte for byte. It goes red with the
    comparison removed.
  - A scenario: two instances (`world.person`) open the same node. The second
    saves first, and the first's save is refused, with both shown.

### F3-b · signing the day's work (high risk; Opus review, Aman approves)

    - when `by` is neither assigned the block nor that person's deputy.

  names each one that is blocked ("n ran, m blocked", rule 3).
- **Program: `POST /v1/node/<id>/sign`**, through `me::with_key`, at
  `results::now_utc()`. The signed file is saved as in F3-a.
- **Closing finding 6 of 171, before anything signs:**

    that unlocks a key or signs carries it. Another local process that calls

  - After five wrong passphrases for one key file, `open` waits 30 seconds

- **Proved by:**

### F3-c · back to the drive (high risk; Opus review, Aman approves)

- **Library: `folder::put_back(copy, drive, me)`** answers a report, one line
  for each file.
  - A file goes back only when all of these hold:
    - it differs from the drive;
    - it carries a current signature, seal or answer by `me`, checked through
      the chain;
    - the drive's bytes still match what `copied.toml` recorded.
  - Every other file is named, with the reason. Nothing is deleted.
  - Each file is written to a temporary name on the drive, then renamed.
- **Program: `POST /v1/put-back`.** It shows the report before anything is
  written, and writes on a second request that names the same files.
- **Proved by:**
  - A file changed on the drive since the copy is not overwritten.
  - A file `me` did not sign is not put back.
  - The signed node is put back, and a second instance that copies again sees
    it in today's view of the group.

### F3-d · asking, as a request in the node file (high risk; Opus review, Aman approves)

The node engineer asks for a contract change (W4) or a breakdown (W13). The
request is written in the node file, signed on its own, and goes back to the
drive with the file. It does not wait for the node to pass its checks: the
node that needs a new contract is often the one that cannot pass.

- **The file (format 3).** `request.kind` takes `contract`, `breakdown` or
  `code`. `breakdown` joins format 3 in the key proof's pull request, so the
  files in `design/` are rewritten once, not twice.
- **Library: `request::ask(copy, path, opened, by, key, at, kind, body, group)`.**
  - It takes the copy's lock and compares `opened`, as a save does. On a
    difference it refuses as *a second writer stopped*, and writes nothing.
  - It refuses:
    - when `group.key(by, key, at)` does not hold;
    - when `by` may not sign the node (`may_sign_node`: its writer, or their
      deputy);
    - an empty body, or a kind other than `contract` or `breakdown`.
  - It adds one open request with an empty answer, and signs it. The
    signature's scope is `request:<uid>`, over the request's row as it is.
    `chain::digest` gains that scope; a request has one revision, `1`, because
    it is never edited.
  - The node's revision does not rise, and nothing in the node's content
    changes, so its signature still holds.
- **Saving (F3-a) keeps every request.** A save that changes or drops a
  request is refused by name. Requests are added only by asking.
- **Back to the drive (F3-c).** A node file goes back also when the drive's
  copy differs from it only by new requests that `me` asked, each open and
  carrying `me`'s signature, checked through the chain.
  - Every request on the drive must still be in the file, unchanged. At a
    higher revision the same holds.
  - A new request by anyone else, or unsigned, keeps the file in the copy,
    named with the reason.
- **Program:**
  - `POST /v1/node/<id>/ask` takes `kind`, `body` and `opened`, through
    `me::with_key`, at `results::now_utc()`.
  - My work, for a group's subsystem engineer: each open request on one of
    the group's nodes, with who asked and when. A request whose signature
    does not check is named as refused, never listed as asked.
  - The node page: *Ask*, with the kind and the words, and the node's
    requests listed with their state.
- **Proved by:**
  - Library tests, each shown red first:
    - a request asked is kept and signed, and the node's signature still
      holds;
    - asked by someone not assigned the node, refused; by their deputy,
      accepted;
    - an empty body, refused;
    - the file changed since it was opened, refused, and nothing written;
    - a request changed after it was signed, refused by the chain;
    - a save that drops or changes a request, refused;
    - put back: a file with only a new signed request goes back;
    - put back: one with a request raised by someone else, unsigned, or with
      a drive request dropped, stays in the copy.
  - A scenario: Nia's node fails its checks, so she cannot sign it. She asks
    for a contract change, and puts the file back. Ola copies again and sees
    the request in My work. Ivo's instance cannot ask on Nia's node.

### F3-e · a lesson's place in the node's file (medium risk; Opus review)

A lesson (`docs/LESSONS.md`) is a row's `lesson.toml`. Today it has no place in
the design's files, so the tool reads none. F3-e gives it one: a `text` of
kind `lesson` in the node's file, scoped to its block. The schema needs no
change, since a text's kind is free and one per block.

- **Served as the folder held it.** `convert::Served` serves a node's
  `lesson` text as `lesson.toml` in the folder the node was converted from,
  as it serves `fixtures.toml` and `parity.csv`. So the loader,
  `GET /v1/lesson/<id>`, the gate's lesson check and the lesson form read it
  as they read one in a checkout. Nothing else in them changes.
- **Signed with the node.** A node's digest covers its texts, so the lesson is
  signed with the node, and a lesson changed after signing breaks that
  signature. It sits outside the sheet hash as before, so no answer moves.
- **Checked where it is written.** `checks::check_node` refuses a lesson that
  does not read (`vleo_sheet::lesson::read`: a misspelt key, markup, an
  untagged claim). What needs the rest of the design, such as a widget naming
  a row that is not there, is checked against today's design by the program
  when the lesson is written, and by the gate once the design holds it.
- **Program: `POST /v1/node/<id>/lesson`** takes a filled lesson form or a bare
  `lesson.toml` (`lesson_form::from_file`), and `opened`. It is checked as the
  gate checks it (`lesson::problems`) against today's tree, and refused with
  every reason. Otherwise it is saved into the node's file in the copy as its
  next revision, through `save::save`, so a second writer is stopped and only
  the node's writer or their deputy writes it. It is not signed; the person
  signs the revision as the day's work (F3-b) and puts it back (F3-c).
- **`docs/LESSONS.md`** says where a lesson now lives and how it arrives.
- **Proved by:**
  - library tests, each shown red first:
    - a node file's lesson is served as its `lesson.toml`, and the loader
      reads it;
    - a lesson that does not read is refused by the node's checks;
    - a lesson changed after signing breaks the node's signature;
  - a program test: a filled form is saved as the next revision; one whose
    widget names a row that is not there is refused with the reason; someone
    not assigned the node is refused; a stale `opened` is a second writer.
